# 인터셉터 패턴 분석 - 훅, 기본 구현, 재시도 결정, 그리고 확장 경로

> [!IMPORTANT]
> **다루는 질문** - 이 레포의 `RequestInterceptor`를 구현하며 나온 질문
>
> - adapt의 역할이 뭔가 -> extension 기본 구현은 왜 있나 -> 인터셉터가 여럿이면 retry는 누가 결정하나 -> **종류가 늘면 프로토콜에 메서드도 늘려야 하나** -> 훅이 정말 늘어나면 pre/post로 쪼개야 하나
>
> - **한 줄 결론**
>   -  인터셉터 = **요청 파이프라인의 정해진 시점(훅)에 정책을 끼우는 패턴.**
>   -  프로토콜은 시점(adapt=전송 직전, retry=실패 직후)을 정의하고, 종류 추가는 "타입 + 배열 한 줄"(프로토콜 불변), 시점 추가만 "훅 + 항등 기본 구현 + NetworkSession 호출 추가" 3종 세트다. 훅이 늘어 쪼갤 때가 오면 **시간(pre/post)이 아니라 역할(Adapting/Retrying/Processing)로** 나눈다 - Alamofire가 예시

## 1. TL;DR

| 질문 | 답 |
|---|---|
| adapt의 역할? | **전송 직전 요청 손보기** - 조립된 요청을 받아 공통 정책(토큰/공통 헤더)을 얹어 돌려주는 공통 통과 지점. 엔드포인트 N개가 각자 선언하면 중복+누락이 생길 수 있어 한곳으로 모은 것 |
| extension 기본 구현의 목적? | 인터셉터가 **필요한 훅만** 구현하게, 기본값은 "안전한 무행동" - adapt는 항등(그대로 통과), retry는 재시도 안 함(.doNotRetry) |
| 인터셉터 여럿이면 retry는? | **전원에게 순서대로 묻되 첫 .retry가 채택된다** (OR 결합 + first-wins). retry 미구현 타입은 기본 구현이 .doNotRetry로 처리 |
| 종류 추가 = 프로토콜 수정? | NO - 새 타입 + 조립부 배열 한 줄. 프로토콜/NetworkSession/기존 인터셉터 무수정 (OCP) |
| 새 훅이 필요하면? | 프로토콜에 요구사항 추가 + **항등 기본 구현**(기존 채택자 무수정 생존) + NetworkSession에 호출 한 줄 추가 - NetworkSession을 수정하는 건 이때뿐 |
| 훅이 많아지면 분리 기준? | **역할(동사) 기준** - RequestAdapter/RequestRetrier처럼. 트리거는 훅 개수가 아니라 "구현체마다 쓰는 훅이 갈리는 정도" |

## 2. 기본 구조 - 시점과 정책의 분리

```
endpoint.urlRequest()          명세 -> 요청 조립
   |
[adapt 훅]  <- AuthToken(토큰 부착) -> APIVersion(버전 헤더) -> ...   <- 정책들
   |
session.data(for:)             전송
   | 실패 시
[retry 훅]  <- TransientRetry(백오프 재시도 결정) -> (미래: TokenRefresh) <- 정책들
```

핵심 분리: **시점(훅)은 프로토콜이, 정책(내용)은 타입이, 목록(무엇을 끼울지)은 Composition Root가** 안다. 파이프라인을 실행하는 NetworkSession은 호출 순서만 알고 내용을 모른다.

```swift
public protocol RequestInterceptor: Sendable {
    func adapt(_ request: URLRequest, endpoint: some NetworkEndpoint) throws -> URLRequest
    func retry(_ endpoint: some NetworkEndpoint, dueTo error: Error, attempt: Int) async -> RetryDecision
}
```

- **adapt = 전송 직전 요청 손보기.** 반환 스타일이라 `request = try interceptor.adapt(request, ...)`로 체인이 자연스럽다 (inout vs 반환의 "여러 개 통과면 반환 체인" 그 기준)
- **retry = 실패 직후 재시도 결정.** async인 이유: "토큰 갱신하고 재시도"처럼 결정 자체가 네트워크를 탈 수 있어서
- 요청을 **바꾸는** 인터셉터와 **지켜보기만 하는** 모니터(NetworkEventMonitor)는 프로토콜을 분리했다. 지켜보는 쪽에도 요청을 수정할 수 있는 메서드를 열어 두면, 언젠가 누군가는 거기서 요청을 수정하게 되기 때문.

## 3. 기본 구현 - "안전한 무행동"의 설계

```swift
extension RequestInterceptor {
    public func adapt(_ request: URLRequest, endpoint: some NetworkEndpoint) throws -> URLRequest {
        request          // 항등(identity) - 체인에 끼어도 영향 0
    }
  
    public func retry(...) async -> RetryDecision {
        .doNotRetry      // 재시도 안 함 - 잊어도 사고가 안 나는 방향
    }
}
```

세 가지 설계 포인트

1. **필요한 훅만 구현** - AuthToken은 adapt만, TransientRetry는 retry만 구현한다. 같은 배열을 두 훅이 다른 목적으로 순회하고, 각자 안 쓰는 훅은 기본 구현이 처리한다

| | adapt 루프 (요청 준비) | retry 루프 (실패 후) |
|---|---|---|
| AuthTokenInterceptor | 토큰 부착 | .doNotRetry (기본 구현) |
| TransientErrorRetryInterceptor | 통과 (기본 구현) | 재시도 결정 |

2. **기본값의 방향** - retry 기본이 `.retry`였다면 아무 인터셉터나 끼우는 순간 모든 실패가 재시도되는 문제 발생
   -  체인의 안전한 기본값은 **항등/재시도 안 함**이어야 한다. 
3. **기본 구현이 동작하려면 선언 위치가 중요하다** - 메서드를 protocol 본문에 선언해 두고 extension에서 기본 구현을 주면, 구현체가 그 메서드를 직접 구현했을 때 구현체 것이 불린다. 반대로 protocol 본문에 선언하지 않고 extension에만 메서드를 두면, 구현체가 같은 이름을 만들어도 `any RequestInterceptor` 타입으로 호출할 때 extension 것이 불린다. 그래서 기본 구현은 항상 "본문에 선언 + extension에 구현" 세트로 만든다.

## 4. 재시도 결정 루프 - 전원에게 묻고 첫 .retry 채택

```swift
private func retryDelay<E: NetworkEndpoint>(_ endpoint: E, dueTo error: Error, attempt: Int) async -> TimeInterval? {
    for interceptor in interceptors {
        if case .retry(let after) = await interceptor.retry(endpoint, dueTo: error, attempt: attempt) {
            return after          // 첫 .retry의 지연시간이 채택 - 이후는 안 물음
        }
    }
    return nil                    // 아무도 재시도를 원하지 않음 -> 에러 그대로 throw
}
```

- **결합 방식은 OR** - 인터셉터가 여럿일 때 하나라도 `.retry`를 반환하면 재시도한다. 전부 `.doNotRetry`일 때만 실패가 확정된다.
- **first-wins라서 순서가 중요해진다** - `.retry`를 반환할 수 있는 인터셉터가 둘이 되면(예: TokenRefresh 추가) **배열에서 앞에 있는 쪽의 지연시간이 채택**된다. 그때는 AppContainer의 배열 순서에 "왜 이 순서인가" 주석이 필요해진다.
- **지연시간(after)을 인터셉터가 정하는 이유** - "몇 초 쉬었다 재시도할지"(백오프 계산)도 재시도 정책의 일부다. NetworkSession은 받은 숫자만큼 기다릴 뿐, 계산 방법은 모른다.

## 5. 확장 경로 1) - 종류 추가 (프로토콜 불변)

```swift
struct APIVersionInterceptor: RequestInterceptor {          // 새 타입
    func adapt(_ request: URLRequest, endpoint: some NetworkEndpoint) throws -> URLRequest {
        var request = request
        request.setValue("2022-11-28", forHTTPHeaderField: "X-GitHub-Api-Version")
        return request
    }
}
// AppContainer - 배열에 한 줄. 다른 파일 수정 0
interceptors: [AuthTokenInterceptor(...), APIVersionInterceptor(), TransientErrorRetryInterceptor()]
```

**새 종류가 생겨도 훅(메서드)을 늘릴 일은 거의 없다** - 401 토큰 갱신 같은 요구도 기존 retry 훅 안에서 "토큰을 갱신한 뒤 `.retry(after: 0)` 반환"으로 해결되므로 새 메서드가 필요 없다. 새 정책 = 새 타입 + 배열 한 줄이고, 프로토콜과 NetworkSession은 그대로다(OCP, 개방-폐쇄 원칙).

## 6. 확장 경로 2) - 시점(훅) 추가 (3종 세트)

응답 복호화처럼 **세 번째 순간**(응답 도착 직후)이 필요해지면

```swift
// 1) 프로토콜에 요구사항 + 2) 항등 기본 구현 (기존 채택자 무수정 생존 = protocol evolution)
func process(_ data: Data, endpoint: some NetworkEndpoint) throws -> Data
extension RequestInterceptor {
    public func process(_ data: Data, endpoint: some NetworkEndpoint) throws -> Data { data }
}
// 3) NetworkSession에 호출 추가 - NetworkSession을 수정하는 건 이때뿐
var data = data
for interceptor in interceptors { data = try interceptor.process(data, endpoint: endpoint) }
```

**NetworkSession을 수정하게 되는 유일한 경우**: 새 *정책*(인터셉터 종류 추가)에는 수정할 일이 없고, 새 *시점*(훅 추가)에만 수정이 필요하다. "요청의 일생에 어떤 순간들이 있는가"는 파이프라인을 실행하는 NetworkSession만 아는 정보이기 때문이다. 다만 시점 추가는 드물고(요청의 일생은 유한하다), 한 번 수정하면 한동안 수정할 일이 없다.

**훅을 추가하기 전에 확인할 것 3가지**: 요청/응답을 바꾸는 시점인가(-> 훅 추가) / 지켜보기만 하는가(-> NetworkEventMonitor 소관) / 파이프라인과 무관한가(-> 인터셉터가 아니라 별도 부품). 이 확인 없이 훅을 쌓으면 메서드만 잔뜩 든 뚱뚱한 프로토콜이 된다.

## 7. 확장 경로 3) - 훅이 많아지면: 역할 기준 분리 (Alamofire의 답)

pre/post(시간) 명명은 "언제"만 말하고 "뭘 하는지"를 안 말한다 - 같은 pre 시점이라도 바꾸기(adapt)와 지켜보기(willSend)는 하는 일이 다르다. **동사(역할)로 나누면 시점은 따라온다:**

```swift
// Alamofire 실제 구조 (개념 요약)
protocol RequestAdapter { func adapt(...) }        // 꾸미는 역할
protocol RequestRetrier { func retry(...) }        // 재시도 판단 역할
protocol RequestInterceptor: RequestAdapter, RequestRetrier {}   // 합성
```

**전환 트리거는 훅 개수가 아니라 사용 패턴**: 훅 2~4개 + 기본 구현이면 단일 프로토콜로 충분하다(기본 구현이 ISP 이득의 8할을 이미 준다). 훅 5~6개를 넘고 **구현체마다 쓰는 훅이 한두 개로 뚜렷이 갈리면** 분리 - 그때부터 채택 선언(`: RequestAdapter`)만 보고 타입의 역할을 알 수 있다는 게 진짜 이득.

분리하면 NetworkSession이 인터셉터를 어떻게 들고 있을지도 갈린다: **역할별 배열**(`[any RequestAdapter]`, `[any RequestRetrier]` - 조립부에서 역할이 드러난다, 권장) vs 배열 하나에 섞어 두고 `as?`로 런타임에 걸러내기(타입으로 표현할 수 있는 정보를 런타임 검사로 미루는 방식이라 비추천).

## 8. 정리

확장은 세 층으로 나뉜다.

1. **새 정책** (공통 헤더, 재시도 규칙 추가) - 프로토콜을 채택한 타입을 하나 만들어 조립부 배열에 끼우면 끝. 프로토콜과 NetworkSession은 수정하지 않는다 (5절).
2. **새 시점** (예: 응답 복호화) - 이때만 프로토콜에 훅을 추가한다. 항등 기본 구현을 세트로 주면 기존 인터셉터들은 수정 없이 살아남는다. Alamofire가 훅을 늘려온 방식 (6절).
3. **훅이 많아져 쪼갤 때** - pre/post 같은 시간 기준이 아니라 Adapter/Retrier처럼 역할 기준으로 나누고 합성한다. 분리 시점은 훅 개수가 아니라 "구현체마다 쓰는 훅이 갈리는 정도"로 판단한다. 이 레포는 훅 2개/구현체 2개라 단일 프로토콜이면 충분하다 (7절).

보충 정리:
- **extension 기본 구현(3절)과 @objc optional의 차이** - @objc optional은 런타임 존재 검사(respondsTo)가 따라오고 클래스 전용이다. 기본 구현은 컴파일 타임에 존재가 보장되고 값 타입에도 쓸 수 있다.
- **인터셉터끼리 순서 의존이 생기면** - 지금은 first-wins와 adapt 체인 순서로 암묵적으로 표현돼 있다. 의존이 진해지면 우선순위 값이나 phase 분리로 명시한다 (7절).
- **로깅을 인터셉터로 만들지 않는 이유** - 로깅은 지켜보기만 하면 되는데, 인터셉터로 만들면 요청을 수정할 수 있는 메서드까지 갖게 된다. 바꾸기/지켜보기를 프로토콜 수준에서 분리한 이유 (2절, NetworkEventMonitor).
