# 인터셉터 패턴 - 훅, 기본 구현, 재시도 결정, 확장 경로

> 2026-07-10, CoreNetwork를 구현하며 정리한 노트
> 관련 소스: [RequestInterceptor.swift](../../Projects/Core/CoreNetwork/Sources/Pipeline/RequestInterceptor.swift) / [NetworkSession.swift](../../Projects/Core/CoreNetwork/Sources/NetworkSession.swift) / [AppContainer.swift](../../Projects/App/GitSearchApp/Sources/AppContainer.swift)

인터셉터는 요청 파이프라인의 정해진 시점에 정책을 끼우는 패턴입니다. 프로토콜이 시점을 정의하고(adapt는 전송 직전, retry는 실패 직후), 정책의 내용은 타입이 갖습니다.

구현하면서 다섯 가지가 걸렸습니다. adapt는 정확히 무슨 역할인가, extension 기본 구현은 왜 두는가, 인터셉터가 여럿이면 retry는 누가 결정하는가, 종류가 늘면 프로토콜에도 메서드를 늘려야 하는가, 훅이 정말 늘어나면 어떻게 쪼개는가.

결론부터 적으면, 종류 추가는 타입 하나와 배열 한 줄이면 되고 프로토콜은 그대로입니다. 시점 추가만 훅과 항등 기본 구현과 NetworkSession 호출을 세트로 요구합니다. 훅이 늘어 쪼갤 때가 오면 시간(pre/post)이 아니라 역할(Adapting/Retrying/Processing)로 나눕니다. Alamofire가 그 예시입니다.

---

## 기본 구조 - 시점과 정책의 분리

```
endpoint.urlRequest()          명세 -> 요청 조립
   |
[adapt 훅]  <- AuthToken(토큰 부착) -> APIVersion(버전 헤더) -> ...   <- 정책들
   |
session.data(for:)             전송
   | 실패 시
[retry 훅]  <- TransientRetry(백오프 재시도 결정) -> (미래: TokenRefresh) <- 정책들
```

시점은 프로토콜이, 정책은 타입이, 무엇을 끼울지는 Composition Root가 압니다. 파이프라인을 실행하는 NetworkSession은 호출 순서만 알고 내용을 모릅니다.

```swift
public protocol RequestInterceptor: Sendable {
    func adapt(_ request: URLRequest, endpoint: some NetworkEndpoint) throws -> URLRequest
    func retry(_ endpoint: some NetworkEndpoint, dueTo error: Error, attempt: Int) async -> RetryDecision
}
```

adapt는 전송 직전에 요청을 손봅니다. 조립된 요청을 받아 토큰이나 공통 헤더 같은 공통 정책을 얹어 돌려줍니다. 엔드포인트마다 각자 선언하면 중복과 누락이 생기니 한곳으로 모았습니다. 반환 스타일이라 `request = try interceptor.adapt(request, ...)`로 체인이 자연스럽게 이어집니다.

retry는 실패 직후 재시도를 결정합니다. async인 이유는 "토큰 갱신하고 재시도"처럼 결정 자체가 네트워크를 탈 수 있어서입니다.

요청을 바꾸는 인터셉터와 지켜보기만 하는 모니터(NetworkEventMonitor)는 프로토콜을 분리했습니다. 지켜보는 쪽에도 요청을 수정할 수 있는 메서드를 열어 두면 언젠가 누군가는 거기서 요청을 수정합니다.

## 기본 구현 - 안전한 무행동

```swift
extension RequestInterceptor {
    public func adapt(_ request: URLRequest, endpoint: some NetworkEndpoint) throws -> URLRequest {
        request          // 항등(identity) - 체인에 끼어도 영향 0
    }
  
    public func retry(...) async -> RetryDecision {
        .doNotRetry      // 재시도 안 함 - 잊어도 사고가 안 나는 방향
    }
}
```

**필요한 훅만 구현하게 합니다.** AuthToken은 adapt만, TransientRetry는 retry만 구현합니다. 같은 배열을 두 훅이 다른 목적으로 순회하고, 각자 안 쓰는 훅은 기본 구현이 처리합니다.

| | adapt 루프 (요청 준비) | retry 루프 (실패 후) |
|---|---|---|
| AuthTokenInterceptor | 토큰 부착 | .doNotRetry (기본 구현) |
| TransientErrorRetryInterceptor | 통과 (기본 구현) | 재시도 결정 |

**기본값의 방향이 중요합니다.** retry 기본이 `.retry`였다면 아무 인터셉터나 끼우는 순간 모든 실패가 재시도됩니다. 체인의 안전한 기본값은 항등과 재시도 안 함이어야 합니다.

**선언 위치가 동작을 가릅니다.** 메서드를 protocol 본문에 선언해 두고 extension에서 기본 구현을 주면, 구현체가 그 메서드를 직접 구현했을 때 구현체 것이 불립니다. 반대로 protocol 본문에 선언하지 않고 extension에만 메서드를 두면, 구현체가 같은 이름을 만들어도 `any RequestInterceptor` 타입으로 호출할 때 extension 것이 불립니다. 그래서 기본 구현은 항상 "본문에 선언, extension에 구현" 세트로 만듭니다.

## 재시도 결정 루프

```swift
private func retryDelay<E: NetworkEndpoint>(_ endpoint: E, dueTo error: Error, attempt: Int) async -> TimeInterval? {
    for interceptor in interceptors {
        if case .retry(let after) = await interceptor.retry(endpoint, dueTo: error, attempt: attempt) {
            return after          // 첫 .retry의 지연시간이 채택 - 이후는 안 물음
        }
    }
    return nil                    // 아무도 재시도를 원하지 않음 -> 에러 그대로 throw
}
```

전원에게 순서대로 묻되 첫 `.retry`를 채택합니다. 결합 방식은 OR이라 하나라도 `.retry`를 반환하면 재시도하고, 전부 `.doNotRetry`일 때만 실패가 확정됩니다.

first-wins이므로 순서가 중요해집니다. `.retry`를 반환할 수 있는 인터셉터가 둘이 되면(TokenRefresh를 추가하는 경우) 배열에서 앞에 있는 쪽의 지연시간이 채택됩니다. 그때는 AppContainer의 배열 순서에 왜 이 순서인지 주석이 필요해집니다.

지연시간을 인터셉터가 정하는 것도 이유가 있습니다. 몇 초 쉬었다 재시도할지, 즉 백오프 계산도 재시도 정책의 일부입니다. NetworkSession은 받은 숫자만큼 기다릴 뿐 계산 방법은 모릅니다.

## 확장 경로 1 - 종류 추가

```swift
struct APIVersionInterceptor: RequestInterceptor {          // 새 타입
    func adapt(_ request: URLRequest, endpoint: some NetworkEndpoint) throws -> URLRequest {
        var request = request
        request.setValue("2022-11-28", forHTTPHeaderField: "X-GitHub-Api-Version")
        return request
    }
}
// AppContainer - 배열에 한 줄. 다른 파일 수정 0
interceptors: [AuthTokenInterceptor(...), APIVersionInterceptor(), TransientErrorRetryInterceptor()]
```

새 종류가 생겨도 훅을 늘릴 일은 거의 없습니다. 401 토큰 갱신 같은 요구도 기존 retry 훅 안에서 토큰을 갱신한 뒤 `.retry(after: 0)`을 반환하면 되므로 새 메서드가 필요 없습니다. 새 정책은 새 타입과 배열 한 줄이고, 프로토콜과 NetworkSession은 그대로입니다(OCP, 개방-폐쇄 원칙).

## 확장 경로 2 - 시점 추가

응답 복호화처럼 세 번째 순간, 그러니까 응답 도착 직후가 필요해지면 세 가지를 세트로 넣습니다.

```swift
// 1) 프로토콜에 요구사항 + 2) 항등 기본 구현 (기존 채택자 무수정 생존 = protocol evolution)
func process(_ data: Data, endpoint: some NetworkEndpoint) throws -> Data
extension RequestInterceptor {
    public func process(_ data: Data, endpoint: some NetworkEndpoint) throws -> Data { data }
}
// 3) NetworkSession에 호출 추가 - NetworkSession을 수정하는 건 이때뿐
var data = data
for interceptor in interceptors { data = try interceptor.process(data, endpoint: endpoint) }
```

NetworkSession을 수정하게 되는 경우는 이때뿐입니다. 새 정책에는 수정할 일이 없고 새 시점에만 수정이 필요합니다. 요청의 일생에 어떤 순간들이 있는지는 파이프라인을 실행하는 NetworkSession만 아는 정보이기 때문입니다. 다만 요청의 일생은 유한하니 시점 추가는 드물고, 한 번 수정하면 한동안 수정할 일이 없습니다.

훅을 추가하기 전에 세 가지를 확인합니다. 요청이나 응답을 바꾸는 시점인지(훅 추가), 지켜보기만 하는지(NetworkEventMonitor 소관), 파이프라인과 무관한지(인터셉터가 아니라 별도 부품). 이 확인 없이 훅을 쌓으면 메서드만 잔뜩 든 뚱뚱한 프로토콜이 됩니다.

## 확장 경로 3 - 훅이 많아지면 역할로 나누기

pre/post 같은 시간 명명은 언제인지만 말하고 무엇을 하는지를 말하지 않습니다. 같은 pre 시점이라도 바꾸기(adapt)와 지켜보기(willSend)는 하는 일이 다릅니다. 동사로 나누면 시점은 따라옵니다.

```swift
// Alamofire 실제 구조 (개념 요약)
protocol RequestAdapter { func adapt(...) }        // 꾸미는 역할
protocol RequestRetrier { func retry(...) }        // 재시도 판단 역할
protocol RequestInterceptor: RequestAdapter, RequestRetrier {}   // 합성
```

전환 트리거는 훅 개수가 아니라 사용 패턴입니다. 훅 2~4개에 기본 구현이면 단일 프로토콜로 충분합니다. 기본 구현이 ISP 이득의 8할을 이미 줍니다. 훅 5~6개를 넘고 구현체마다 쓰는 훅이 한두 개로 뚜렷이 갈리면 그때 분리합니다. 채택 선언 `: RequestAdapter`만 보고 타입의 역할을 알 수 있다는 게 진짜 이득입니다.

분리하면 NetworkSession이 인터셉터를 어떻게 들고 있을지도 갈립니다. 역할별 배열(`[any RequestAdapter]`, `[any RequestRetrier]`)로 두면 조립부에서 역할이 드러나므로 이쪽을 권합니다. 배열 하나에 섞어 두고 `as?`로 런타임에 걸러내는 방식은 타입으로 표현할 수 있는 정보를 런타임 검사로 미루는 것이라 추천하지 않습니다.

## 정리

확장은 세 층으로 나뉩니다.

**새 정책**을 넣을 때는, 그러니까 공통 헤더나 재시도 규칙을 추가할 때는 프로토콜을 채택한 타입을 하나 만들어 조립부 배열에 끼우면 끝입니다. 프로토콜과 NetworkSession은 수정하지 않습니다.

**새 시점**이 생길 때만 프로토콜에 훅을 추가합니다. 응답 복호화가 그런 경우입니다. 항등 기본 구현을 세트로 주면 기존 인터셉터들은 수정 없이 살아남습니다. Alamofire가 훅을 늘려온 방식입니다.

**훅이 많아져 쪼갤 때**는 pre/post 같은 시간 기준이 아니라 Adapter와 Retrier처럼 역할 기준으로 나누고 합성합니다. 분리 시점은 훅 개수가 아니라 구현체마다 쓰는 훅이 갈리는 정도로 판단합니다. 이 레포는 훅 2개에 구현체 2개라 단일 프로토콜이면 충분합니다.

두 가지를 덧붙입니다. extension 기본 구현과 `@objc optional`은 다릅니다. `@objc optional`은 런타임 존재 검사(respondsTo)가 따라오고 클래스 전용입니다. 기본 구현은 컴파일 타임에 존재가 보장되고 값 타입에도 쓸 수 있습니다.

로깅을 인터셉터로 만들지 않은 이유도 같은 맥락입니다. 로깅은 지켜보기만 하면 되는데 인터셉터로 만들면 요청을 수정할 수 있는 메서드까지 갖게 됩니다. 바꾸기와 지켜보기를 프로토콜 수준에서 나눈 이유입니다.
