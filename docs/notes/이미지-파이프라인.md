# 아바타 이미지 파이프라인 - 2계층 캐시/다운샘플/off-main/prefetch (WWDC18 대비)

> 관련 소스: [CellProfileLoader.swift](../../Projects/Feature/FeatureSearch/Sources/Presentation/ImageLoading/CellProfileLoader.swift) / [ImageCache.swift](../../Projects/Feature/FeatureSearch/Sources/Presentation/ImageLoading/ImageCache.swift) / [ImageDownsampler.swift](../../Projects/Feature/FeatureSearch/Sources/Presentation/ImageLoading/ImageDownsampler.swift)

> [!IMPORTANT]
> **다루는 질문** - 유저 목록 셀에 아바타를 붙이며 나올 수 있는 궁금증
>
> - `CellProfileLoader`/`ImageCache`/`ImageDownsampler` 세 파일은 각각 무엇을 담당하나?
> - 캐시가 왜 **두 층**인가(메모리/디스크가 아니라)? `UIImage(data:)`로 바로 그리면 왜 안 되나? 셀 재사용으로 남의 아바타가 잠깐 뜨는 잔상은 어떻게 막나?
> - **한 줄 결론**: 목록+비동기 이미지는 **네 가지 비용**(재다운로드/재디코딩/메모리/재사용 잔상)을 동시에 낸다.
> - **바이트 캐시**(Data 레이어, 다운로드 회피/영속)와 **디코딩 이미지 캐시**(Presentation, 디코딩 회피/휘발)의 **2계층**이 앞의 셋을 줄이고, `CellProfileLoader`의 **방어 4종**(representedID 대조/행별 취소/userID별 태스크 공유/off-main 다운샘플)이 잔상과 스레드 비용을 막는다.
> - 핵심은 `ImageDownsampler`다 - `UIImage(data:)`의 **풀 디코딩 함정**을 ImageIO 썸네일로 우회해 826KB->106KB(약 7.8배)로 줄이고, `nonisolated async`(SE-0338)로 협조적 풀에서 돌려 스크롤을 막지 않는다. **WWDC18 "Image and Graphics Best Practices"(세션 219)의 정석을 네트워크/Swift Concurrency 시대로 옮긴** 구현이다.

## 1. TL;DR

| 비용 | 누가 줄이나 | 어떻게 |
|---|---|---|
| **재다운로드** | Data 바이트 캐시 (`ProfileCaching`/`DiskProfileCache`) | 원본 `Data`를 userID별로 메모리/디스크에 저장 -> 네트워크 스킵 |
| **재디코딩** | Presentation 이미지 캐시 (`Cache<Int, UIImage>`) | 디코딩/다운샘플된 `UIImage`를 메모리에 저장 -> 히트 시 동기 즉시 반영 |
| **메모리** | `ImageDownsampler` | 풀 디코딩 대신 **셀 크기 썸네일**로 디코딩 (826KB->106KB, 약 7.8배) |
| **재사용 잔상** | `CellProfileLoader` 방어 4종 | `representedID` 기록->완료 시 대조, 행별 취소, 태스크 공유 |
| **스크롤 jank** | off-main 다운샘플 | `nonisolated async`로 협조적 풀에서 디코딩, `sending`으로 메인에 인계 |

## 2. 문제 - 목록 + 비동기 이미지의 네 비용

유저 목록을 스크롤한다. 각 셀엔 원격 아바타 이미지가 붙는다.

| 비용 | 아무 처리 없이 구현하면 생기는 증상 |
|---|---|
| **재다운로드** | 같은 유저가 다시 화면에 들어올 때마다 CDN(Content Delivery Network - 이미지 같은 정적 파일을 원본 서버 대신 곳곳의 캐시 서버에서 내려주는 인프라)에 재요청 -> 셀이 뜰 때마다 다시 기다리고 같은 바이트를 매번 다시 받는다 (아바타는 CDN 서빙이라 **검색 API rate limit과는 무관** - 4절 각주) |
| **재디코딩** | 캐시된 이미지라도 매번 JPEG를 픽셀로 푸는 디코딩 반복 |
| **메모리** | `UIImage(data:)`가 **원본 해상도 그대로** 풀 디코딩 -> 55pt 슬롯에 460px 비트맵(826KB)을 올림 -> 수십 셀이면 그것만으로 수십 MB를 차지한다 |
| **재사용 잔상** | 셀은 재사용된다. A행 다운로드가 끝날 때 그 셀은 이미 B유저를 그리는 중 -> **B 자리에 A 아바타**가 잠깐 뜬다 |

여기에 **스크롤 jank**가 겹친다. 디코딩/다운샘플을 **메인 스레드**에서 하면 스크롤이 프레임을 떨군다. WWDC18이 지목한 바로 그 문제다: 이미지의 실제 비용은 파일 크기가 아니라 **디코딩된 비트맵 크기와 그 디코딩이 도는 위치**다. 

**목표**: 네 비용을 계층 하나가 하나씩 맡도록 나누고, 디코딩은 무조건 off-main으로 민다.

## 3. 파이프라인 전경 - ImageLoading 3파일 + fetchProfile seam

Presentation의 `ImageLoading/` 디렉토리에 세 파일이 있고 역할이 깔끔히 갈린다.

| 파일 | 타입 | 역할 | 한 줄 |
|---|---|---|---|
| `CellProfileLoader.swift` | `@MainActor final class` | **조율(orchestration)** | 언제 받아오고, 어느 셀에 꽂고, 언제 취소할지. "어떻게 받아오는지"는 모름 |
| `ImageCache.swift` | `final class Cache<Key, Value>` | **디코딩 이미지 메모리 캐시** | 다운샘플된 `UIImage`를 `NSCache`로 보관 + 히트율 통계 |
| `ImageDownsampler.swift` | `enum` (caseless) | **변환(transform)** | `Data` -> 셀 크기로 다운샘플된 `sending UIImage?`. 순수 함수 |

세 파일은 Presentation 안에서 닫혀 있고 원본 바이트가 필요할 때는 **`fetchProfile` seam**(주입된 클로저)으로 Data 레이어에 닿는다.

```swift
// CellProfileLoader.swift - 로더가 아는 유일한 외부 통로
private let fetchProfile: (GithubUser) async throws -> Data
```

로더는 이 클로저 뒤에 네트워크/캐시/레포가 있는지 **전혀 모른다**. VC가 주입한다.

```swift
// SearchUserViewController.swift
private lazy var avatarLoader = CellProfileLoader { [viewModel] user in
    try await viewModel.avatarData(for: user)
}
```

체인: `CellProfileLoader.fetchProfile` -> `viewModel.avatarData(for:)` -> `fetchProfileUseCase.execute(imagePath:id:)` -> `ProfileImageRepository.fetchProfile`.

## 4. 역할별 2계층 캐시 

캐시가 **두 개**인데, 나뉘는 축은 메모리/디스크가 아니라 **무엇을 담는가**다.

| | **바이트 캐시** (Data 레이어) | **이미지 캐시** (Presentation) |
|---|---|---|
| 타입 | `ProfileCaching` (`InMemoryProfileCache`/`DiskProfileCache`) | `Cache<Int, UIImage>` |
| 담는 것 | **원본 `Data`** (인코딩된 JPEG/PNG 바이트) | **디코딩/다운샘플된 `UIImage`** |
| 줄이는 비용 | **재다운로드** (CDN 지연/대역폭) | **재디코딩** (CPU) |
| 지속성 | `DiskProfileCache`는 **영속**(앱 재시작 후 남음) | **휘발**(NSCache, 메모리 압박 시 자동 퇴거) |
| 키 | `userID: Int` -> `<id>.img` 파일 | `userID: Int` (박싱) |
| 위치 | `Data/Cache/` | `Presentation/ImageLoading/` (`CellProfileLoader.swift`) |

### 3계층 조회 흐름

요청 하나는 다음 순서로 조회한다 - **싼 계층부터 먼저, 비싼 계층은 마지막**이다.

```
1)  메모리 이미지 캐시  ->  히트: 디코딩 없이 UIImage 즉시 (동기)
        | 미스
2)  바이트 캐시(Disk/InMemory)  ->  히트: 네트워크 없이 Data 확보 -> 다운샘플만
        | 미스
3)  네트워크  ->  Data 받고 -> 바이트 캐시에 store -> 다운샘플
```

- **1) 메모리 이미지 캐시 히트** - 로더에서 **동기 즉시** 반영. 디코딩조차 없다.
  ```swift
  // CellProfileLoader.swift
  if let image = imageCache.value(forKey: user.id) {
      cell.setProfile(image)     // 즉시 return, 다운샘플 안 함
      return
  }
  ```
- **2) 바이트 캐시 히트** - 레포에서 네트워크를 스킵한다.
  
  ```swift
  // ProfileImageRepository.swift
  if let cached = cache.data(forUserID: userID) {
      return cached             // 네트워크 안 감
  }
  ```
- **3) 네트워크** - 받은 뒤 반드시 바이트 캐시에 되쓴다.
  ```swift
  // ProfileImageRepository.swift
  let data = try await session.requestRawData(SearchUserAPI.downloadImage(url: url))
  cache.store(data, forUserID: userID)
  ```

### 왜 둘 다 필요한가

바이트 캐시만 있으면? 히트해도 **매번 다시 디코딩/다운샘플**해야 한다(CPU 낭비). 이미지 캐시만 있으면? 메모리 압박으로 `UIImage`가 퇴거되면 **다시 네트워크**를 타야 한다(디스크 영속성이 없으니). 둘을 겹치면 "디코딩된 건 빠르게, 없으면 최소한 다운로드는 스킵"이라는 **점진적 폴백**이 된다.

### 무효화(staleness)와 URLCache를 안 쓴 이유

솔직한 한계 하나: 바이트 캐시는 `userID: Int` -> `<id>.img`로만 키를 잡는다(`DiskProfileCache.fileURL`). 그런데 GitHub 아바타 URL은 유저가 사진을 바꾸면 `?v=4`->`?v=5`처럼 **버전 파라미터가 바뀐다**. id만 키로 쓰면 그 변화를 못 보고 **옛 아바타가 계속 뜨는** 고전적 staleness 버그가 생긴다.

- **왜 그래도 괜찮나 (트레이드오프)**: 아바타 교체는 드물고 저장 위치가 `Caches`라 시스템이 언제든 비운다(그때 새로 받는다). "정확한 최신성"보다 "단순/확정적 영속"을 택한 의도적 단순화.
- **정확히 반영하려면**: 키에 URL 전체나 `?v=` 해시를 섞으면 된다(교체 시 새 키 -> 새 다운로드).
- **왜 `URLCache`가 아니라 자체 캐시인가**: `URLCache`는 HTTP 캐시 규칙에 묶여 서버 헤더(`Cache-Control`/`ETag`)를 존중한다 - 서버가 캐시를 금지하면 저장 자체가 안 되고 TTL 제어가 어렵다. 대신 `ETag` 조건부 재검증으로 **교체를 자동 감지**하는 이점이 있다. 자체 바이트 캐시는 그 자동 재검증을 포기하는 대신 **id 키로 확정적 영속/단순 제어**를 얻는다 - 이 파이프라인의 선택이고, 그 대가가 위 staleness다.

> [!NOTE] rate limit은 검색 API의 문제지 아바타의 문제가 아니다
> 아바타는 **CDN**(`avatars.githubusercontent.com`, Fastly)에서 서빙된다 - 시간당 요청 한도가 걸리는 **REST/검색 API**(`api.github.com`)가 아니다. 그러니 아바타 재다운로드가 **검색 rate limit을 소모하지 않는다.** 바이트 캐시의 진짜 이득은 rate limit 절약이 아니라 **지연/대역폭/CDN 왕복 제거**다. (rate limit이 실제로 걸리는 건 검색어 입력마다의 유저 검색 호출이고, 그건 ViewModel의 debounce가 줄인다 - 별개 층.)

## 5. ImageDownsampler 뜯어보기 - 파이프라인의 핵심

`ImageDownsampler`는 caseless `enum`(인스턴스 없음)에 static 함수 하나만 있는 **순수 함수**다.

```swift
// ImageDownsampler.swift
static func makeImage(
    from data: Data,
    pointSize: CGSize,
    scale: CGFloat
) async -> sending UIImage?
```

### 5-1. 왜 다운샘플인가 - `UIImage(data:)`의 풀 디코딩 함정

`UIImage(data:)`로 그리면 **원본 픽셀 해상도 그대로** 메모리에 비트맵을 푼다. 파일이 아무리 작은 JPEG라도, 디코딩되면 `width x height x 4바이트(RGBA 8bpc)`가 통째로 올라온다. **파일 크기와 디코딩된 메모리는 무관**하다.

| 항목 | 값 | 계산 |
|---|---|---|
| 원본 아바타 픽셀 (예) | 460x460 | GitHub 원본은 수백 px대 (identicon 약 420px, `?s=`로 조절) |
| 풀 디코딩 메모리 | **약 826KB** | 460 x 460 x 4 = 846,400 B / 1024 = 826.6 KB |
| 목표 슬롯 | 55pt (3x = 165px) | 55 x 3 = 165 px |
| 다운샘플 후 메모리 | **약 106KB** | 165 x 165 x 4 = 108,900 B / 1024 = 106.3 KB |
| **절약** | **약 7.7~8배** | 846,400 / 108,900 = 7.77배 (차원비 460^2/165^2도 동일) |

> [!NOTE] 이 수치는 RGBA 8bpc 풀 디코딩(bitmap) 기준의 이론값
> 실제로는 row bytes 정렬 패딩/컬러스페이스/ImageIO 캐시 여부에 따라 소폭 달라진다. 그리고 이건 **디코딩된 in-memory 크기** 기준이라 JPEG **파일 크기**와는 별개다. 목록에 수십 개 셀이 뜬다고 생각하면, 셀당 720KB 차이가 곧 수십 MB 차이다 - 그래서 다운샘플이 메모리의 핵심 레버다.

### 5-2. ImageIO 썸네일이 핵심인 이유

`ImageDownsampler`는 `UIImage(data:)`를 안 쓴다. 대신 **ImageIO의 `CGImageSourceCreateThumbnailAtIndex`** 로 **풀 디코딩을 건너뛰고 곧바로 썸네일 크기로 디코딩**한다. 즉 460px 비트맵을 만든 뒤 줄이는 게 아니라, 처음부터 165px만 디코딩한다.

```swift
// ImageDownsampler.swift (발췌)
let maxPixel = max(pointSize.width, pointSize.height) * scale   // L26: 165

let sourceOptions = [kCGImageSourceShouldCache: false] as CFDictionary   // L29
let source = CGImageSourceCreateWithData(data as CFData, sourceOptions)  // L30
// ...
let thumbnailOptions = [
    kCGImageSourceCreateThumbnailFromImageAlways: true,   // 원본이 커도 항상 새로 생성
    kCGImageSourceCreateThumbnailWithTransform: true,     // EXIF 회전 반영
    kCGImageSourceShouldCacheImmediately: true,           // 여기(off-main)서 디코딩 완료
    kCGImageSourceThumbnailMaxPixelSize: maxPixel,        // 최대 변 = 165px
] as CFDictionary
let cgImage = CGImageSourceCreateThumbnailAtIndex(source, 0, thumbnailOptions)   // L41
```

### 5-3. 옵션 4개의 의미 (한 곳은 특히 중요)

| 옵션 | 의미 | 왜 |
|---|---|---|
| `kCGImageSourceShouldCache: false` (소스) | 원본 전체 이미지의 **디코딩 결과를 소스에 캐싱하지 않음** (디코딩을 막는 게 아니라 "디코딩된 형태 보관" 여부만 제어) | 썸네일만 뽑고 원본은 버린다. 썸네일 경로라 사실상 방어적(no-op에 가까움) |
| `...ThumbnailFromImageAlways: true` | 파일에 박힌 EXIF 썸네일을 무시하고 **항상 전체 이미지로부터** 새로 생성 | 박힌 썸네일은 크기/품질을 못 믿는다. (반대는 `...IfAbsent`) |
| `...ThumbnailWithTransform: true` | **EXIF orientation을 반영해** 썸네일을 회전/변환 | 사진이 눕지 않게 (6절에서 상술) |
| **`...ShouldCacheImmediately: true`** | **생성 시점에 즉시 디코딩/캐시** (기본은 lazy) | **가장 중요.** "지금, 이 off-main 스레드에서" 디코딩을 끝낸다 |
| `...ThumbnailMaxPixelSize: 165` | 썸네일의 **최대 변 길이(px)** = width/height 중 긴 쪽을 이 값 이하로 | 정확히 셀 크기만큼만 디코딩 |

> [!TIP] `ShouldCache: false`와 `ShouldCacheImmediately: true`는 모순이 아니다
> 얼핏 "캐시 하지 마"와 "즉시 캐시 해"가 충돌해 보이지만, **대상이 다르다.** `kCGImageSourceShouldCache: false`는 **소스(원본 전체 이미지)** 를 캐싱하지 말라는 것 - 원본은 버릴 거니까. `kCGImageSourceShouldCacheImmediately: true`는 **결과 썸네일**을 지금 즉시 디코딩해 두라는 것. 즉 "원본은 캐시 마, 하지만 내가 뽑은 썸네일은 여기서 디코딩을 끝내라". 핵심은 **디코딩 시점을 off-main으로 못박는 것** - 이걸 lazy로 두면 메인 스레드가 나중에 그릴 때 디코딩이 터져 jank가 난다.

### 5-4. UIImage 생성 - scale이 왜 중요한가

```swift
// ImageDownsampler.swift
return UIImage(cgImage: cgImage, scale: scale, orientation: .up)
```

**`scale`을 반드시 명시해야 한다.** `UIImage(cgImage:)`(scale 인자 없는 버전)는 내부적으로 `scale = 1.0`을 가정한다. `size(pt) = pixel / scale`이므로, 165px CGImage를 scale=1로 감싸면 논리 크기가 **165pt**가 된다 - 55pt 슬롯에 3배 크게 렌더된다.

> [!WARNING] "3x 기기에서 3배 크게"의 진짜 원인은 DPR이 아니라 `scale` 프로퍼티
> 흔한 오해: "3x 레티나라 크게 나온다". 정확한 인과는 **UIImage의 `scale` 프로퍼티**다. 55pt 슬롯에 맞추려면 `scale = 3.0`(=디바이스 scale)으로 감싸 165px / 3 = **55pt**가 되게 해야 한다. 표시가 커지는 건 UIImage의 `scale`을 1로 둔 탓이지, 기기 배율 자체 때문이 아니다. 그래서 `makeImage`는 `scale`을 파라미터로 받아 명시적으로 넘긴다(로더는 `scale = 3` 기본, `CellProfileLoader.swift`).

> [!WARNING] `scale = 3` 하드코딩은 단순화 - 프로덕션은 디바이스 scale을 읽어야
> 로더는 `scale = 3`을 기본으로 박아 둔다(`CellProfileLoader.swift` 주석도 "화면 scale 추적 배선을 생략한 트레이드오프"라 인정). 2x 기기(구형/다수 iPad)에선 필요보다 큰 165px를 디코딩해 **메모리를 조금 더 쓴다**(3x 최대치라 화질은 안전). 정확히는 `traitCollection.displayScale`(또는 `window.screen.scale`)을 런타임에 읽어 주입해야 하며, 5-4절의 "scale 반드시 명시" 논지와 완전히 일관되려면 그 값도 실제 디바이스 scale이어야 한다.

### 5-5. off-main - nonisolated async가 스크롤을 살린다

시그니처를 다시 보면 `@MainActor` 로더가 아닌 곳에서 도는 설계다.

```swift
// ImageDownsampler.makeImage: nonisolated async -> sending UIImage?
```

`ImageDownsampler.makeImage`는 **nonisolated**(어느 액터에도 안 묶임)이자 **async**다. `@MainActor`인 `CellProfileLoader`가 이걸 `await`로 부르면, 함수 본문은 **호출자 액터(메인)가 아니라 협조적 스레드 풀(제네릭 executor)에서 실행**된다 - 자동으로 off-main hop한다. 디코딩이라는 CPU 작업이 메인을 비우고 도니 스크롤이 안 막힌다.

```swift
// CellProfileLoader.swift (주석: "디코딩/다운샘플은 off-main - 스크롤을 막지 않는다")
let image = await ImageDownsampler.makeImage(
    from: data,
    pointSize: owner.pointSize,
    scale: owner.scale
)
```

결과 `UIImage`는 non-Sendable이다. 그런데 이걸 off-main에서 만들어 `@MainActor` 영역으로 넘겨야 한다 - 여기서 **`sending`(SE-0430)** 이 등장한다. 반환 타입 `sending UIImage?`는 "이 값의 region을 호출자에게 **이양**한다"(공유가 아니라 1회 이양이며 `consuming` 소유권과는 다름)고 컴파일러에 보장하므로, non-Sendable인 UIImage를 액터 경계 밖으로 안전히 넘길 수 있다. Swift 6 strict-concurrency에서 이 경계가 **컴파일로 통과함이 확인됐다**(주석 `ImageDownsampler.swift`). `sending`의 정체/검증(`-typecheck` 함정)/off-main 전제는 [swift6-sendable](swift6-sendable.md) 노트의 sending 절 참고.

> [!NOTE] SE-0338의 "off-caller"는 버전 단서가 필요하다
> nonisolated async가 호출자 액터를 벗어나 제네릭 executor에서 도는 건 **SE-0338**("Clarify the Execution of Non-Actor-Isolated Async Functions") 이후의 기본 동작이다. 단, **Swift 6.2의 SE-0461**(`NonisolatedNonsendingByDefault` upcoming feature)을 켜거나 `nonisolated(nonsending)`을 붙이면 **호출자의 executor에서 실행**되도록 바뀐다. 그러니 "nonisolated async는 무조건 off-caller"라고 단정하면 6.2+ 문맥에서 부정확하다. 이 코드가 off-main으로 도는 건 **SE-0338 기본 동작 + `nonisolated(nonsending)`을 안 붙였기 때문**이라고 말해야 정밀하다. (협조적 풀은 코어 수만큼의 스레드로 모든 async 작업을 돌리는 런타임 풀이다.)

### 5-6. caseless enum - 순수 함수라 테스트가 쉽다

`ImageDownsampler`는 `enum`(case 없음)이라 **인스턴스를 못 만든다**. 상태 없는 static 함수 하나뿐 - 입력(`Data`, `pointSize`, `scale`)만으로 출력이 결정되는 순수 함수다. 의존성도 없고 격리도 없으니, 테스트에서 `Data` 하나 넣고 결과 `UIImage`의 크기만 확인하면 된다. "변환"이라는 역할이 타입 형태에 그대로 드러난다.

## 6. EXIF Orientation - 왜 `.up`인가

`kCGImageSourceCreateThumbnailWithTransform: true`와 마지막 `orientation: .up`은 한 쌍이다. 이유를 알아야 한다.

- **센서는 픽셀을 캡처된 물리 방향 그대로 저장**한다. "표시할 때 어떻게 회전/미러링할지"는 **메타데이터 태그(EXIF Orientation)로만** 기록한다. 값은 **1~8**의 정수다.

  | 값 | 의미 |
  |---|---|
  | 1 | 정상 (회전 없음) |
  | 3 | 180도 |
  | 6 | 시계 방향 90도 |
  | 8 | 반시계 방향 90도 |
  | 2/4/5/7 | 미러링 포함 |

- **`CGImage`는 순수 픽셀 버퍼라 orientation 개념이 없다.** 그래서 태그를 무시하고 픽셀만 뽑으면 사진이 **눕거나 뒤집혀** 나온다 - 세로로 찍은 사진이 옆으로 눕는, 흔히 겪는 버그다.
- 해결: `...WithTransform: true`가 **EXIF 방향을 픽셀에 구워 넣는다(bake)**. 이미 똑바로 선 픽셀이 나오니, 마지막에 `UIImage(cgImage:scale:orientation: .up)` - **더 회전할 필요 없음(.up)** 이 맞다.

> [!TIP] 아바타는 대개 orientation 1이지만 방어적으로 켠다
> GitHub 아바타는 보통 정상 방향(1)이라 변환이 필요 없을 때가 많다. 그래도 `WithTransform`을 켜 두면, 사용자가 회전 태그가 붙은 사진을 아바타로 올려도 안전하다. 비용은 거의 없고 버그 하나를 원천 차단한다. (`UIImage`는 CGImage와 별도로 `imageOrientation`을 들고 UIKit 렌더 시 자동 반영하지만, CGImage를 직접 그리거나 픽셀을 뽑으면 방향 정보가 사라진다 - 그래서 파이프라인 안에서 굽는 게 안전하다.)

## 7. CellProfileLoader의 방어 4종

`@MainActor final class CellProfileLoader`(`CellProfileLoader.swift`)가 조율을 맡는다. 핵심 상태:

```swift
// CellProfileLoader.swift
private let imageCache = Cache<Int, UIImage>(countLimit: 500, totalCostLimit: 64 * 1024 * 1024)  // L29
private var tasks: [Int: ManagedTask] = [:]              // L32: userID별 다운로드 슬롯
private var representedCells: [Int: WeakCell] = [:]      // L36: id -> 지금 그 id를 그리는 셀(약참조)
```

키를 착각하기 쉽다: **두 표 모두 키가 `Int`(= `user.id`)다 - 셀이 키가 아니다.** 즉 "셀마다 태스크"가 아니라 **유저당 태스크 최대 1개**(single-flight)이고, `tasks`에는 보이는 것(load)과 안 보이는 것(prefetch-only)이 섞여 있으며, `representedCells`는 그중 "결과를 꽂을 셀이 있는" 부분집합만 담는다. 두 표의 조합이 곧 상태다:

| 상황 | `tasks[id]` | `representedCells[id]` | 결말 |
|---|---|---|---|
| load 진행 중 (캐시 미스) | 실행 중 | 셀 있음 | `deliver`가 그 셀에 반영 |
| prefetch-only 진행 중 | 실행 중 | 없음 | 캐시만 데움 - `deliver`의 guard가 조용히 종료 |
| 캐시 히트 | 태스크 자체가 없음 | 없음 | `load`가 동기 즉시 반영 |
| 배달 직후 | **idle 슬롯 잔류** | 없음 (`defer` 말소, 11절 NOTE) | 슬롯 정리는 `cancel` 몫 (아래 방어 3) NOTE) |

> [!NOTE] 두 조력 타입 - `ManagedTask`와 `WeakCell`
> **`ManagedTask`** (방어 2)3)의 중심, `Core/CoreDesignSystem`): Swift `Task`를 감싼 `@MainActor` 클래스. 계약 넷 - 1) `isRunning`(도는 중인가) 2) `runIfIdle`(이미 돌면 시작 안 함=중복 제거)/`replace`(취소 후 교체) 3) `cancel()`이 `Task.cancel()`을 불러 구조적 동시성을 타고 **URLSession까지 취소 전파** 4) `deinit`에서 보유 Task 취소(화면이 죽으면 요청도 끝). 자세히는 [managedtask](managedtask.md), owner 편의형 `runIfIdle(with:)`는 [owner-패턴](owner-패턴.md).
> **`WeakCell`**: 셀을 담는 박스(`struct WeakCell { weak var cell: UserListCell? }`). 로더가 셀을 **강참조하면 UITableView 재사용과 충돌**(셀이 풀로 못 돌아가 수명이 왜곡)하므로 `weak`으로 잡고, 완료 시 `?.cell`이 nil이면(이미 해제) 조용히 버린다 - 방어 1)의 `representedID` 대조와 짝을 이룬다.

### 방어 1) 재사용 잔상 - representedID 기록 -> 완료 시 대조

셀은 재사용된다. A 다운로드가 끝날 때 그 셀이 이미 B를 그리고 있으면 잔상이 뜬다. 막는 법: **셀에 지금 그리는 id를 도장 찍고, 완료 시 도장이 그대로인지 대조**한다.

```swift
// load 진입 (CellProfileLoader.swift)
cell.representedID = user.id            // 이 셀이 지금 표시 중인 id 기록

// deliver 완료 시 (CellProfileLoader.swift)
defer { representedCells[id] = nil }
guard let cell = representedCells[id]?.cell, cell.representedID == id else { return }
if let image { cell.setProfile(image) }
else if failed { cell.setProfile(nil) }   // 실패 -> 회색 플레이스홀더
```

`representedCells[id]?.cell`이 살아 있고 **`cell.representedID == id`일 때만** 반영한다. 셀이 이미 B로 재사용됐으면 `representedID != id`라 조용히 버린다. 남의 아바타가 뜰 일이 없다.

### 방어 2) 행별 취소 - URLSession까지 전파

화면 밖으로 나간 행의 다운로드는 취소한다. VC의 `didEndDisplaying`에서 `cancelLoad(forID:)`를 부른다.

```swift
// cancel (CellProfileLoader.swift)
tasks[id]?.cancel()        // ManagedTask 취소 -> URLSession 요청까지 전파
tasks[id] = nil
representedCells[id] = nil
```

취소는 `ManagedTask`를 통해 **URLSession 요청까지** 내려간다 - 헛된 대역폭을 안 쓴다.

### 방어 3) prefetch/load가 userID별 태스크 공유 - 중복 제거

prefetch(8절)가 미리 받기 시작한 유저를, 스크롤이 따라잡아 실제 load가 요청하면? **다운로드를 두 번 하면 안 된다.** userID별 슬롯(`ManagedTask`)이 이를 합류시킨다.

```swift
// startIfNeeded (CellProfileLoader.swift)
let slot = tasks[user.id] ?? ManagedTask()
tasks[user.id] = slot
slot.runIfIdle(with: self) { owner in
    // 이미 그 id를 받는 중이면 새로 시작하지 않음 -> 다운로드 1회를 prefetch/load가 공유
    ...
}
```

`runIfIdle`은 슬롯이 이미 도는 중이면 **새 작업을 안 만든다**. prefetch가 시작한 태스크에 load가 얹혀 결과를 나눠 갖는다. 완료 시 `deliver`가 `representedCells` 매핑을 보고 "지금 그 id 보는 셀"에만 반영한다.

> [!NOTE] deliver는 슬롯(`tasks[id]`)을 지우지 않는다
> `deliver`는 `representedCells[id]`만 지우고 `tasks[id]`는 **남긴다**. 이유: 실행 중 자기 슬롯을 해제하면 `ManagedTask`의 deinit이 자신을 취소해 버린다(`CellProfileLoader.swift` 주석). 그래서 슬롯 정리는 `cancel`에게만 맡기고, 그전엔 **idle 슬롯으로 남아 `runIfIdle` 재사용**의 발판이 된다.

### 방어 4) 다운샘플 + 이미지 캐시 - cost는 디코딩 비트맵 크기

받은 `Data`를 5절의 다운샘플러로 off-main 변환한 뒤, 결과 `UIImage`를 이미지 캐시에 넣는다. 이때 **cost를 디코딩된 실제 메모리로** 계산해 `totalCostLimit`(64MB)이 진짜 메모리를 반영하게 한다.

```swift
// CellProfileLoader.swift
guard !Task.isCancelled else { return }
let cost = image.cgImage.map { $0.bytesPerRow * $0.height } ?? 0   // 디코딩 비트맵 크기
owner.imageCache.insert(image, forKey: user.id, cost: cost)
owner.deliver(user.id, image: image, failed: false)
```

`bytesPerRow * height`가 곧 그 이미지가 점유하는 바이트다. cgImage가 없으면 0. `Cache.insert`가 이 값을 `NSCache.setObject(_:forKey:cost:)`에 그대로 전달한다(`ImageCache.swift`).

> [!TIP] NSCache 위에 얹은 얇은 래퍼 - 키 박싱과 통계
> `Cache<Key, Value>`는 `NSCache<WrappedKey, Entry>`를 감싼다. NSCache는 **키/값 모두 클래스(AnyObject)** 여야 해서(`class NSCache<KeyType, ObjectType> where KeyType: AnyObject, ObjectType: AnyObject`), `Int` 키를 `WrappedKey: NSObject`로, 값을 `Entry`로 박싱한다(`ImageCache.swift`). NSCache는 **내부적으로 thread-safe**(호출자가 락을 걸 필요 없음 - 내부에서 자체 동기화; "락 없음"이 아니다)이고 메모리 압박 시 **자동 퇴거**하되 **엄격한 LRU는 아니다**(퇴거 순서 미보장). 래퍼는 여기에 `CacheStatistics`(hits/misses/hitRate)를 얹어 히트율을 관측한다(`ImageCache.swift`).

> [!NOTE] 실패/로딩 상태 - "다섯 번째 경로"도 대칭으로
> 네 비용 외에 실패/로딩도 처리된다. `fetchProfile`가 throw하면 `startIfNeeded`의 catch가 갈린다(`CellProfileLoader.swift`): **`CancellationError`는 침묵**(화면 밖으로 나가 취소된 정상 경로 - 셀 손대지 않음), **그 외 에러는 `deliver(..., failed: true)`** -> 회색 플레이스홀더(`setProfile(nil)`). 실패한 userID를 **캐시하지 않으므로(negative caching 없음)** 그 셀이 다시 나타나면 재요청된다 - 별도 backoff 없이 "재등장이 곧 재시도". 로딩 중 초기 표시는 캐시 미스 시 `cell.setProfileLoading()`(`load`, `CellProfileLoader.swift`).

## 8. Prefetch - 스크롤을 앞질러 받기

`UITableViewDataSourcePrefetching`으로 곧 보일 행의 아바타를 **미리** 받는다. dataSource와 별개로 배선한다.

```swift
// SearchUserViewController.swift
tableView.prefetchDataSource = self

// prefetch / cancel (SearchUserViewController.swift)
func tableView(_ tableView: UITableView, prefetchRowsAt indexPaths: [IndexPath]) {
    for indexPath in indexPaths {
        guard let user = dataSource.itemIdentifier(for: indexPath) else { continue }
        avatarLoader.prefetch(user)                     // L384
    }
}
func tableView(_ tableView: UITableView, cancelPrefetchingForRowsAt indexPaths: [IndexPath]) {
    for indexPath in indexPaths {
        guard let user = dataSource.itemIdentifier(for: indexPath) else { continue }
        avatarLoader.cancelPrefetch(forID: user.id)     // L391
    }
}
```

prefetch는 셀을 안 붙이고 **태스크만** 시작한다 - 그리고 load와 **같은 `startIfNeeded`**를 타므로(7절 방어 3)) 스크롤이 따라잡아도 다운로드가 합쳐진다(헛일 방지).

```swift
// prefetch (CellProfileLoader.swift)
guard imageCache.value(forKey: user.id) == nil else { return }   // 이미 있으면 스킵
startIfNeeded(user)                                              // 셀 미등록, 태스크만
```

### 8-1. 입구 guard - 프리페치는 "히트가 곧 완료"

prefetch의 유일한 목표는 캐시 데우기다. 이미 캐시에 있으면 **목표가 이미 달성된 상태** - 그래서 첫 줄 guard가 즉시 끝낸다. 이 guard가 없으면 `startIfNeeded`가 idle 슬롯에 새 작업을 시작해 **디스크 읽기 + off-main 다운샘플 + 재-insert를 통째로 다시** 돌린다(바이트 캐시 덕에 네트워크는 면하더라도 전부 헛일). UIKit은 같은 행을 **여러 번** prefetch 요청할 수 있으므로(스크롤 방향이 바뀔 때마다 예측 갱신) 가장 싼 검사(메모리 조회)로 입구에서 차단한다. `load`의 같은 검사와 다른 점: load는 히트 시 "셀에 꽂기"라는 할 일이 남지만, prefetch는 꽂을 셀이 없으니 **히트 = 그 자체로 완료**다.

> [!WARNING] cancelPrefetch는 실제 load를 취소하지 않는다
> prefetch 취소가 진짜 load까지 죽이면 안 된다. 그래서 셀이 붙어 있으면(=실제 load 중이면) **취소를 건너뛴다**.
> ```swift
> // cancelPrefetch (CellProfileLoader.swift)
> guard representedCells[id]?.cell == nil else { return }   // 셀 붙어 있으면 = 진짜 load -> 보호
> cancel(id)                                                // prefetch-only일 때만 취소
> ```
> 반면 화면에서 실제로 사라진 행은 `cancelLoad`(->`cancel`)로 확실히 취소한다(`didEndDisplaying`, `SearchUserViewController.swift`).

두 guard를 한 쌍으로 보면 - **prefetch는 명령이 아니라 힌트**고, 힌트는 이득만 주고 해를 끼치면 안 된다. 입구 guard(8-1절)가 "이득 없는 일 금지"(중복 작업 차단), `cancelPrefetch`의 guard가 "남의 일 죽이기 금지"(공유 태스크 보호) - **무해성 계약의 양쪽 절반**이다. 태스크 공유(7절 방어 3))의 이득을 취한 대가가 이 소유권 검사고, 조건 불충족 시 no-op이므로 두 API 모두 UIKit이 언제/몇 번 불러도 안전하다(호출 타이밍에 대한 신뢰 불요).

## 9. 시간축 시나리오 - 합류/취소/재사용 레이스

7절의 방어들과 8절의 prefetch는 따로 보면 당연해 보이지만, 실전 난도는 **시간축에서 서로 겹칠 때** 나온다. 먼저 외부 진입점 - 행(row)의 일생이 그대로 로더의 공개 API 4개다:

| 행의 일생 | UIKit 콜백 | 로더 호출 |
|---|---|---|
| "곧 보일 것 같다" (예측) | `prefetchRowsAt` (`SearchUserViewController.swift`) | `prefetch(user)` |
| "예측 취소" | `cancelPrefetchingForRowsAt` (`:389`) | `cancelPrefetch(forID:)` |
| "셀을 만들라" | diffable **cellProvider** (`:78-91`) | `load(user, into: cell)` |
| "화면에서 사라졌다" | `didEndDisplaying` (`:359-365`) | `cancelLoad(forID:)` |

> [!NOTE] load는 willDisplay가 아니라 cellProvider에서 불린다
> 이 프로젝트의 `willDisplay`는 페이징 트리거 전용이다 - "셀을 만들라는 질문(cellProvider, 순수 함수여야 함)"과 "행이 보인다는 사건(delegate)"의 분리(`SearchUserViewController.swift` 주석). 아바타 로딩은 셀 구성의 일부라 cellProvider(클래식 `cellForRowAt` 자리)에 탄다. 그리고 `didEndDisplaying`이 취소할 id를 알아내는 방법이 `cell.representedID` 읽기 - 도장의 **두 번째 용도**다(첫째는 7절 방어 1)의 잔상 방어).

### 9-1. prefetch 선행 -> load 합류 - 다운로드 1회 공유

```
t0  예측     prefetch(u7): 캐시 미스 -> tasks[7] 슬롯 생성, 다운로드 시작 (셀 없음 -> 대기표 없음)
t1  행 도달  load(u7, cellX): 도장 7 -> 캐시 미스 -> 스피너 + representedCells[7] = cellX
            -> startIfNeeded -> tasks[7] 이미 있음 -> runIfIdle: 실행 중 -> 아무것도 안 함
t2  완료     (t0에 시작된 그 태스크가) 다운샘플 -> 캐시 insert -> deliver(7):
            대기표에서 cellX 발견, 도장 7 == 7 -> setProfile 성공 - 다운로드는 처음부터 끝까지 1회
```

이 '아무것도 안 함'의 실체는 `ManagedTask.runIfIdle` 첫 줄 `guard task == nil else { return }` - **이 한 줄이 합류의 전부**다. load가 밖에서 해 둔 일(대기표 등록)만으로, 남(prefetch)이 시작한 태스크의 결과를 받는다. 태스크가 셀을 캡처하지 않고 완료 시 대기표를 조회하는 설계(7절)라서 가능하다.

### 9-2. 화면 이탈 - 취소의 전파

```
t0  load(u7, cellX): 다운로드 진행 중
t1  스크롤로 행 이탈 -> didEndDisplaying: cell.representedID(=7) 읽음
                    -> cancelLoad(7) -> cancel(7): ManagedTask.cancel()
                       -> 구조적 동시성 타고 URLSession 요청까지 실제 중단 (대역폭 회수)
                       -> tasks[7]/representedCells[7] 제거
t2  태스크의 await가 CancellationError로 튐 -> catch: 침묵 - 셀 안 건드림, deliver 안 탐
```

취소가 "표시 안 함"이 아니라 **대역폭 회수**인 이유: CoreNetwork가 `URLError(.cancelled)`를 `CancellationError`로 정규화해 되던지고, ManagedTask 계열의 catch 한 곳으로 수렴한다([managedtask](managedtask.md) 노트 참고).

### 9-3. 재사용 잔상 레이스 - 이중 방어

```
t0  load(u7, cellX): 느린 다운로드
t1  행 이탈 -> didEndDisplaying -> cancelLoad(7)            [1차 방어: 취소]
    cellX 재사용 준비 -> prepareForReuse: representedID = nil (UserListCell.swift)
t2  cellX가 u9용으로 재사용 -> load(u9, cellX): 도장 = 9
t3  u7 결과가 그래도 도착했다면 -> deliver(7):
    대기표는 이미 비었고, 설령 남았어도 도장 9 != 7        [2차 방어: 대조]
    -> 조용히 버림 - u9 자리에 u7 아바타가 뜰 길이 없다
```

각 시점의 `tasks`/`representedCells` 조합은 7절의 4-상태 표로 확인하면 된다. off-main 구간(다운샘플)이 실제로 몇 개의 스레드에서 도는지는 실측으로 30개 Task가 스레드 10개(= 코어 수)로 처리됐다.

## 10. WWDC18 정석 <-> 우리 구현 대조

이 파이프라인의 기반은 **WWDC18 "Image and Graphics Best Practices"(세션 219)** 다. 옵션 세트와 ImageIO 호출은 **그 세션의 정석 그대로**다 - 하지만 네트워크/Swift Concurrency 시대에 맞게 네 곳을 갈아끼웠다.

### 같은 점 (WWDC18 정석)

- `CGImageSourceCreateThumbnailAtIndex` + `kCGImageSourceCreateThumbnailFromImageAlways`/`WithTransform`/`ShouldCacheImmediately`/`ThumbnailMaxPixelSize` **옵션 세트 동일**.
- **다운샘플로 디코딩 메모리를 줄이고, 디코딩을 off-main으로 미는** 두 큰 원칙 동일.
- 블로그(WWDC18 요약)가 제시한 두 CPU 개선 - **Prefetching + Background 디코딩** - 이 파이프라인이 **둘 다** 구현.

### 다른 점

| 축 | WWDC18 정석 | 이 구현 | 왜 |
|---|---|---|---|
| **소스** | 로컬 파일 `URL` | **네트워크 바이트 `Data`** (`CGImageSourceCreateWithData`) | 아바타는 원격 -> Data 레이어 바이트 캐시가 앞단 |
| **off-main** | GCD serial `DispatchQueue` | **`nonisolated async` 협조적 풀** (SE-0338) | 스레드 폭발을 **구조적으로 회피**, serial보다 코어 병렬로 우수 |
| **손상 데이터** | force-unwrap `!` (예제 단순화) | **`guard let` + nil 반환** (`sending UIImage?`) | 깨진 바이트에도 크래시 없이 회색 플레이스홀더 |
| **UIImage 생성** | `UIImage(cgImage:)` scale=1 | **`scale`/`orientation` 명시** | 3x 기기 3배 렌더 버그/눕는 사진 방어 (5-4절, 6절) |

> [!NOTE] 협조적 풀이 GCD serial queue보다 나은 이유 - 스레드 폭발 방지
> WWDC18 예제의 GCD serial queue에 디코딩을 몰면, 동시 다발 다운샘플이 큐에 쌓이거나(직렬 병목) 여러 concurrent 큐로 흩뿌리면 **스레드 폭발(thread explosion)** 위험이 생긴다. Swift Concurrency의 협조적 스레드 풀은 **스레드 폭을 대략 코어 수로 제한**하고, task가 `await`에서 논블로킹으로 양보하는 걸 전제로 설계돼 스레드 폭발을 **구조적으로 방지**한다(WWDC21 "Swift concurrency: Behind the scenes"). 단, 이 캡은 **논블로킹 사용 전제**다 - 협조적 풀 안에서 `sleep`/세마포어/동기 I/O로 블로킹하면 런타임이 forward progress를 위해 스레드를 더 만들 수 있어 캡이 절대적이진 않다. 다운샘플은 CPU 작업이라 이 계약을 지킨다. 직렬화가 필요하면 serial queue 대신 **actor**를 쓰면 되지만, actor는 serial queue와 **동치가 아니다**(재진입성/순서 보장이 다름) - 이건 별도로 구분해야 한다.

## 11. 메서드 레퍼런스 - CellProfileLoader

> [!NOTE] 이 절의 목적
> 3절~10절은 "2계층 캐시/방어 4종"이라는 **개념 축**으로 흩어 설명했다. 여기서는 같은 타입을 **멤버 축**으로, 소스 등장 순서대로 시그니처->역할->핵심 본문으로 한 번에 훑는다. 개념 맥락은 각 항목의 `-> N절` 표기로 되돌아간다. (`CellProfileLoader`는 `@MainActor final class` - 모든 멤버가 MainActor 직렬 실행이라 이 타입엔 락이 없다.)

> [!NOTE] "represented"라는 이름 - AppKit에서 온 관례
> represent = 나타내다/대표하다. `representedID`는 "이 셀이 지금 **나타내는(대표하는)** 대상의 id"다. 이 접두어는 Apple MVC 어휘의 유산 - AppKit의 `NSViewController.representedObject`("이 뷰가 표현하는 모델 객체")/`NSMenuItem.representedObject`가 원조다. 같은 관계를 양쪽에서 본 것: `cell.representedID`는 셀 쪽 시점("나는 지금 누굴 그리나"), `representedCells[id]`는 로더 쪽 시점("그 id는 어느 셀이 기다리나"). 도장은 덤으로 `didEndDisplaying`이 "이 셀이 나갈 때 무엇을 취소할지" 알아내는 열쇠이기도 하다(`SearchUserViewController.swift` - 도장의 두 번째 용도, 9절 NOTE).

### 조립/관측 (2)

| 멤버 (source 순) | 시그니처 | 역할 |
|---|---|---|
| `init` | `init(scale: CGFloat = 3, fetchProfile: @escaping (GithubUser) async throws -> Data)` | **조립.** `scale` 기본 3, `pointSize`를 `UserListCell.profileSize`(= **55pt**, CoreDesignSystem 공개 상수 `UserListCell.swift`)로 고정, 다운로드 seam(`fetchProfile`)을 보관. seam엔 기본값을 안 둬 **항상 주입**받는다 - 계층 분리/테스트의 축(-> 3절). |
| `cacheStatistics` | `var cacheStatistics: CacheStatistics { imageCache.statistics }` | **관측 창구**(디버그/데모). 이미지 캐시의 hits/misses/hitRate를 `imageCache.statistics` 그대로 노출 - 파이프라인이 재디코딩을 실제로 얼마나 줄였는지 계측(-> 7절 통계 TIP). |

### 공개 로딩 API - VC가 부르는 4개

| 멤버 | 시그니처 | 역할 | 되짚기 |
|---|---|---|---|
| `load` | `func load(_ user: GithubUser, into cell: UserListCell)` | **보이는 셀 로딩** - 아래 4단계 | 4절/7절 1) |
| `prefetch` | `func prefetch(_ user: GithubUser)` | **곧 보일 행 미리 받기** - 캐시에 있으면 스킵, 없으면 **셀 없이** 태스크만 시작 | 8절 |
| `cancelPrefetch` | `func cancelPrefetch(forID id: Int)` | **prefetch만 취소** - 셀이 붙어 있으면(=진짜 load) 보호하고 건너뜀 | 8절 |
| `cancelLoad` | `func cancelLoad(forID id: Int)` | **화면 이탈 취소** - 본문은 `cancel(id)` 한 줄. private `cancel`을 VC(`didEndDisplaying`)가 부를 수 있게 연 **공개 이름**일 뿐 | 7절 2) |

> [!NOTE] 세 취소 함수의 분업 - 공개 2 + 내부 1
> `cancelLoad`(화면 이탈)와 `cancelPrefetch`(prefetch 임박 해제)는 **공개 진입점**이고, 실제 정리는 둘 다 private `cancel(_:)` 하나로 수렴한다. 차이는 **가드**뿐: `cancelPrefetch`는 셀이 안 붙어 있을 때만(prefetch-only) 취소하고, `cancelLoad`는 무조건 취소한다. 이름을 나눈 이유는 **호출 맥락**(prefetch API의 취소 콜백 vs `didEndDisplaying`)이 달라 오용을 줄이기 위함이다.

#### `load(_:into:)`의 4단계 (가장 자주 불리는 진입점)

```swift
// CellProfileLoader.swift
func load(_ user: GithubUser, into cell: UserListCell) {
    cell.representedID = user.id                       // 1) 도장: 이 셀이 지금 그리는 id (방어1))
    if let image = imageCache.value(forKey: user.id) { // 2) 메모리 이미지 히트?
        cell.setProfile(image); return                  //    -> 디코딩 0, 동기 즉시 반영 후 종료
    }
    cell.setProfileLoading()                            // 3)-a 로딩 표시(자리 잡기)
    representedCells[user.id] = WeakCell(cell: cell)   // 3)-b "이 id는 이 셀이 기다린다" 등록(약참조)
    startIfNeeded(user)                                // 4) userID별 다운로드 슬롯 보장(prefetch와 공유)
}
```
읽는 순서 그대로가 곧 우선순위다 - **가장 싼 경로(캐시 히트)를 먼저** 치고 빠지고, 미스일 때만 로딩 표시/셀 등록/다운로드로 내려간다. 2)에서 조기 return하므로 히트 시엔 `representedCells` 등록조차 없다(즉시 끝나 대조가 불필요).

### 내부 private (3)

| 멤버 | 시그니처 | 역할 | 되짚기 |
|---|---|---|---|
| `startIfNeeded` | `private func startIfNeeded(_ user: GithubUser)` | **userID별 태스크 보장(single-flight).** `runIfIdle`로 이미 도는 유저는 재시작 안 함. 클로저 본문: `fetchProfile`(Data) -> **off-main 다운샘플** -> `Task.isCancelled` 가드 -> cost 계산/`imageCache.insert` -> `deliver`. `catch`가 `CancellationError`(침묵)와 그 외(실패 전달)로 분기 | 5-5절/7절 3)4) |
| `deliver` | `private func deliver(_ id: Int, image: UIImage?, failed: Bool)` | **결과를 "아직 그 id를 그리는 셀"에만 반영.** `representedCells[id]?.cell`이 살아 있고 `cell.representedID == id`일 때만 `setProfile`. `defer`로 `representedCells[id]`만 비우고 **`tasks[id]`는 남긴다**(실행 중 슬롯 해제 시 deinit 자기취소 방지) | 7절 1)/7절 NOTE |
| `cancel` | `private func cancel(_ id: Int)` | **슬롯/매핑 정리.** `tasks[id]?.cancel()`(-> ManagedTask -> 구조적 동시성 -> **URLSession까지 취소 전파**) 후 `tasks[id]`/`representedCells[id]` 제거 | 7절 2) |

> [!NOTE] `deliver`의 `defer { representedCells[id] = nil }` - 전 경로 말소
> `representedCells`는 "표시 중" 표가 아니라 **pending 배달 대기표**다(표시 중은 `cell.representedID`의 일). 배달을 시도한 순간 - 성공이든, 셀이 사라져 못 꽂았든 - 대기는 끝났고, 항목을 남기면 표가 거짓말을 한다. 종료 경로가 둘(guard 실패 early return / 정상 반영)이라 `defer`로 **어느 경로든 반드시** 말소한다. `defer`는 첫 줄에 선언해도 실행은 스코프 종료 직전이라(Swift 공식 문서 Deferred Actions 절 - "어떤 방식으로 떠나든 직전에 실행") **guard가 지우기 전 값을 먼저 읽을 수 있다** - "읽기는 지금, 말소는 나갈 때"를 한 줄로 쓰는 문법.
> 명시적 말소가 필수인 근본 이유: **weak는 dealloc에만 반응하고 셀 '재사용'은 감지하지 못한다**(실측: 같은 셀 객체가 다른 id를 그리기 시작해도 박스의 `cell`은 non-nil 유지, Swift 6.3.2). 재사용 풀의 셀은 테이블이 살아 있는 한 사실상 안 죽으므로, 방치된 항목은 "살아 있는 셀"을 무기한 가리키고 - 이 표를 신뢰하는 `cancelPrefetch`의 guard가 "진짜 load가 붙어 있다"고 **오판해 취소를 건너뛰게** 된다. 짝이 되는 비대칭: 같은 함수가 `tasks[id]`는 **안** 지운다(7절 방어 3) NOTE의 deinit 자기취소) - "대기표는 반드시, 슬롯은 절대"가 `deliver`의 계약이다.
