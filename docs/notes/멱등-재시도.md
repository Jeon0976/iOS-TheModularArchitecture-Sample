# 멱등성은 왜 인터셉터가 아닌가 - 사실과 행동을 나누는 기준

> 2026-07-10, CoreNetwork를 구현하며 정리한 노트
> 관련 소스: [NetworkEndpoint.swift](../../Projects/Core/CoreNetwork/Sources/NetworkEndpoint.swift) / [TransientErrorRetryInterceptor.swift](../../Projects/Core/CoreNetwork/Sources/Pipeline/TransientErrorRetryInterceptor.swift)

토큰 부착을 `AuthTokenInterceptor`로 분리하고 나니 자연스럽게 다음 질문이 따라왔습니다. 멱등성 관리도 인터셉터로 분리해야 하지 않나?

분리할 필요가 없다는 게 결론입니다. 인터셉터로 나가는 것은 행동, 그러니까 요청을 바꾸거나 재시도를 결정하는 일이고, 멱등성은 엔드포인트가 스스로 선언하는 사실입니다. 멱등성에 딸린 행동인 재시도 게이트는 이미 `TransientErrorRetryInterceptor` 안에 있습니다.

게이트만 따로 빼면 안 되는 이유가 하나 더 있습니다. 재시도 여부는 인터셉터 전원에게 물어서 하나라도 `.retry`면 재시도하는 방식이라, 게이트가 `.doNotRetry`를 반환해도 다른 인터셉터가 `.retry`를 반환하면 재시도가 실행됩니다. 게이트가 뚫립니다.

## 대상 코드

```swift
// CoreNetwork/Sources/NetworkEndpoint.swift - 사실의 자리
public protocol NetworkEndpoint: Sendable {
    // ...
    /// 이 요청에 Authorization 헤더를 자동 부착할지, 기본 true
    var requiresAuth: Bool { get }
    /// 이 요청을 자동으로 한 번 더 보내도 안전한가(멱등), 재시도 정책의 게이트
    var isIdempotent: Bool { get }
}

extension NetworkEndpoint {
    /// 기본값을 선언이 아니라 HTTP 메서드에서 유도한다 (RFC 7231/9110의 정의 그대로)
    public var isIdempotent: Bool {
        switch method {
        case .get, .put, .delete: true      // 몇 번을 보내도 서버 상태가 같다
        case .post, .patch: false           // 부수효과(토큰 발급, 생성...)가 중복될 수 있다
        }
    }
}
```

```swift
// CoreNetwork/Sources/Pipeline/RequestInterceptor.swift - 행동의 자리
public protocol RequestInterceptor: Sendable {
    /// 전송 직전의 요청을 받아 꾸민 요청을 돌려준다 (예: Authorization 부착)
    func adapt(_ request: URLRequest, endpoint: some NetworkEndpoint) throws -> URLRequest
    /// 요청이 실패했을 때 재시도 여부를 결정한다. 주의: 하나라도 .retry면 다시 보낸다 (OR 결합)
    func retry(_ endpoint: some NetworkEndpoint, dueTo error: Error, attempt: Int) async -> RetryDecision
}
```

```swift
// CoreNetwork/Sources/Pipeline/TransientErrorRetryInterceptor.swift - 게이트의 실제 위치
// 멱등 게이트: 비멱등 요청이면 에러 종류를 보기도 전에 재시도를 포기한다
guard endpoint.isIdempotent else { return .doNotRetry }
```

## 사실과 행동, 코드 배치의 기준

### 토큰을 인터셉터로 분리했다는 말의 정확한 의미

토큰 처리는 두 조각인데 인터셉터로 나간 것은 행동뿐입니다.

| 조각 | 내용 | 위치 |
|---|---|---|
| 사실 | "이 요청은 인증이 필요하다" | `NetworkEndpoint.requiresAuth` - 엔드포인트에 남았습니다 |
| 행동 | 그 사실을 보고 Authorization 헤더를 붙입니다 | `AuthTokenInterceptor.adapt` - 이것만 나갔습니다 |

멱등성도 이미 같은 배치입니다.

| 조각 | 내용 | 위치 |
|---|---|---|
| 사실 | "이 요청은 두 번 보내도 안전하다" | `NetworkEndpoint.isIdempotent` (HTTP 메서드에서 기본값 유도) |
| 행동 | 그 사실을 보고 재시도를 결정합니다 | `TransientErrorRetryInterceptor.retry` - 이미 인터셉터 |

"토큰처럼 멱등성도 분리하자"는 이미 끝난 일이고, `isIdempotent`를 인터셉터로 옮기면 오히려 이 대칭이 깨집니다.

### 왜 사실은 엔드포인트에, 행동은 인터셉터에 두나

사실은 자기 자신을 아는 곳에 둡니다. "검색 API가 멱등한가"는 그 API의 속성입니다. 엔드포인트 선언부인 `SearchUserAPI`는 method, path, headers 같은 사실을 이미 선언하고 있고 `requiresAuth`와 `isIdempotent`도 그 목록의 연장입니다.

행동은 파이프라인에 둡니다. 정책은 교체하고 조합하고 테스트하는 단위입니다. 새 정책은 새 타입 하나에 Composition Root의 배열 한 줄이면 되고 NetworkSession은 수정하지 않습니다. 정책 단위 테스트도 여기서 나옵니다.

사실의 선언 부담도 설계에 포함됩니다. `isIdempotent` 기본값을 [RFC 9110 9.2.2절](https://www.rfc-editor.org/rfc/rfc9110#section-9.2.2)의 멱등 메서드 정의 그대로 HTTP 메서드에서 유도하므로, OAuth 토큰 교환(POST)은 아무 선언 없이도 자동 재시도에서 빠집니다.

## 분리 가능 여부를 정하는 결합 규칙

`RequestInterceptor.retry`의 규칙은 "하나라도 `.retry`면 다시 보낸다"입니다. 즉 `.doNotRetry`는 재시도를 막는다는 뜻이 아니라 "나는 재시도할 이유가 없다"일 뿐이라서, 다른 인터셉터의 `.retry`를 막지 못합니다.

### 게이트를 분리하면 생기는 구멍

멱등 게이트만 `IdempotencyGateInterceptor`로 빼는 안을 그대로 굴려보면 이렇게 됩니다.

```
POST 요청이 badConnection으로 실패했다.

IdempotencyGateInterceptor        -> POST라서 .doNotRetry   (재시도 이유 없음)
TransientErrorRetryInterceptor    -> 일시적 에러라서 .retry  (게이트가 빠진 버전)
-----------------------------------------------------
OR 결합                            -> 재시도 실행 !!  게이트가 뚫렸다
```

POST 재전송은 부수효과의 중복 실행입니다. 토큰 이중 발급이나 결제 이중 청구가 이 부류입니다. 게이트는 재시도를 결정하는 정책 안쪽의 첫 번째 guard여야만 안전합니다. 실제 코드가 앞의 세 번째 코드 블록처럼 그렇게 돼 있습니다.

### 같은 함정이 나오는 자리들

결정을 합치는 시스템에서 이 판단을 별도 컴포넌트로 분리해도 되는지는 결합 규칙이 정합니다.

- any-allow(OR): 하나만 허용해도 통과합니다. 거부 조건은 분리할 수 없고 허용하는 쪽 내부의 guard로 둬야 합니다
- all-must-allow(AND): 전원이 허용해야 통과합니다. 거부 조건을 독립 컴포넌트로 분리할 수 있습니다

재시도 정책과 권한 체크 체인, 유효성 검사 파이프라인이 전부 같은 구조의 문제입니다. 분리 리팩터링 전에 결정이 어떻게 합쳐지는지부터 확인해야 합니다.

## 사실이 행동이 되는 시점 - Idempotency-Key

멱등성 관련 코드가 인터셉터 자격을 얻는 순간은 행동이 생길 때입니다. 대표 사례가 Stripe 등이 지원하는 Idempotency-Key 패턴입니다. 클라이언트가 POST에 고유 키 헤더를 실으면 서버가 같은 키의 중복 실행을 막아 주기 때문에, 비멱등 요청도 안전하게 재시도할 수 있습니다. 이런 API를 쓰게 되면 두 가지가 생깁니다.

- `IdempotencyKeyInterceptor` - `adapt`에서 POST 요청에 UUID 키 헤더를 부착합니다. 요청을 바꾸는 행동이니 인터셉터 자격이 생깁니다
- 해당 엔드포인트만 `isIdempotent = true`로 오버라이드하면 재시도 게이트가 열립니다

예외가 필요한 엔드포인트가 생기면 그 엔드포인트만 `isIdempotent`를 오버라이드하면 됩니다. GitHub API는 이 키를 지원하지 않으므로 지금은 만들지 않습니다. 사용처가 생기면 그때 만듭니다.

## Alamofire와의 대응

| 이 레포 | Alamofire | 역할 |
|---|---|---|
| `RequestInterceptor.adapt` | `RequestAdapter.adapt` | 전송 직전 요청 변형 |
| `RequestInterceptor.retry` + `RetryDecision` | `RequestRetrier.retry` + `RetryResult` | 실패 후 재시도 결정 (백오프 포함) |
| 두 훅을 한 protocol에 + 기본 구현 | `Interceptor` (Adapter+Retrier 합성) | 필요한 훅만 구현 |

구조가 같으므로 "Alamofire 없이 만들면 어떻게 되나"와 "Alamofire의 adapt와 retry는 왜 그렇게 생겼나"에 같은 답을 쓸 수 있습니다.

## 정리

재시도는 인터셉터 체인의 retry 훅에서 결정하고 멱등성은 엔드포인트가 `isIdempotent`로 선언합니다. 배치 기준은 사실과 행동의 분리입니다. 인증이 필요한지, 두 번 보내도 안전한지는 엔드포인트의 자기 선언이고, 그 사실을 보고 헤더를 붙이거나 재시도를 결정하는 것은 파이프라인의 정책입니다.

멱등 게이트를 별도 인터셉터로 빼지 않은 이유는 결정이 합쳐지는 방식에 있습니다. 이 파이프라인은 하나라도 `.retry`면 재시도하는 OR 결합이라 `.doNotRetry`가 재시도를 막지 못하고, 게이트를 분리하면 다른 인터셉터의 `.retry`에 뚫립니다. 그래서 재시도를 결정하는 정책 안의 첫 guard로 뒀습니다.

멱등성 기본값은 RFC 9110의 정의대로 HTTP 메서드에서 유도합니다. 그래서 OAuth 토큰 교환 같은 POST는 아무 선언 없이도 자동 재시도에서 빠집니다.

몇 가지를 덧붙입니다.

POST 재시도가 위험한 것은 비멱등이라 생성이나 발급, 청구 같은 부수효과가 중복 실행될 수 있어서입니다. 특히 타임아웃은 서버가 처리하지 못했다는 뜻이 아니라 응답만 못 받았다는 뜻일 수 있어서 더 위험합니다.

rate limit(403/429)은 멱등 GET인데도 재시도하지 않습니다. 멱등 게이트와 별개의 조건입니다. 기계적 재시도는 제한을 더 길게 만들 뿐이라, 게이트를 통과한 뒤에도 에러 종류로 다시 거릅니다.

백오프는 `RetryDecision.retry(after:)`에 실려 옵니다. 지연 계산도 정책의 일부라 인터셉터가 계산하고, NetworkSession은 받은 숫자만큼 기다릴 뿐입니다. 0.5초에서 1.0초, 2.0초로 지수 증가합니다.
