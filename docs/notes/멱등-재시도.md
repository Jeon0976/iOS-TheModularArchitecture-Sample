# 멱등성은 왜 인터셉터가 아닌가 - 사실과 행동을 나누는 기준, 재시도 결정이 합쳐지는 방식

> [!NOTE]
> 2026-07-10, CoreNetwork를 구현하며 정리한 노트
> 관련 소스: [NetworkEndpoint.swift](../../Projects/Core/CoreNetwork/Sources/NetworkEndpoint.swift) / [TransientErrorRetryInterceptor.swift](../../Projects/Core/CoreNetwork/Sources/Pipeline/TransientErrorRetryInterceptor.swift)

> [!IMPORTANT]
> **다루는 질문** - 토큰 부착을 `AuthTokenInterceptor`로 분리하면서 든 의문점
>
> - **"멱등성 관리도 인터셉터로 분리해야 하지 않나?"** 
> - **한 줄 결론**: 인터셉터로 분리할 필요가 없다.
> -  인터셉터로 나가는 것은 **행동**(요청을 바꾸거나 재시도를 결정)이고, 멱등성은 엔드포인트가 스스로 **선언**하는 **사실**이다. 멱등성의 행동(재시도 게이트)은 이미 `TransientErrorRetryInterceptor` 안에 있다. 게이트만 따로 인터셉터로 빼면 안 되는 이유: 재시도 여부는 인터셉터 전원에게 물어서 **하나라도 `.retry`면 재시도**하는 방식이라, 게이트가 `.doNotRetry`를 반환해도 다른 인터셉터가 `.retry`를 반환하면 재시도가 실행된다(게이트가 뚫린다).

## 1. TL;DR

| 질문 | 답 |
|---|---|
| 인터셉터의 자격 기준? | **행동이 있는가** - 요청을 바꾸거나(`adapt`) 재시도를 결정하거나(`retry`). "토큰이니까/멱등성이니까"가 아니다 |
| 멱등성은 뭔가? | 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같다는 성질. 이 레포에서는 엔드포인트가 `isIdempotent`로 스스로 선언한다 - `requiresAuth`와 같은 부류 |
| 토큰과의 대칭? | `requiresAuth`(사실, 엔드포인트) <-> `AuthTokenInterceptor`(행동) = `isIdempotent`(사실, 엔드포인트) <-> `TransientErrorRetryInterceptor`(행동) - **분리는 이미 완료** |
| 게이트만 인터셉터로 빼면? | `.doNotRetry`는 "재시도 금지"가 아니라 **"나는 재시도할 이유가 없다"일 뿐**이다 - 하나라도 `.retry`면 재시도하는 OR 결합이라, 다른 인터셉터의 `.retry`가 이겨서 POST가 재시도된다 (4절) |
| 멱등성 코드가 인터셉터가 되는 시점? | 행동이 생길 때 - Idempotency-Key 헤더를 **부착**하는 순간 (5절) |
| 다른 곳에서도 나오는 문제인가? | 여러 부품의 결정을 합칠 때 "하나라도 허용이면 허용(OR)"인지 "전원 허용해야 허용(AND)"인지에 따라, 거부 조건을 별도 부품으로 분리할 수 있는지가 달라진다. 재시도만이 아니라 권한 체크/유효성 검사 체인에서도 똑같이 나온다 (4절) |

## 2. 대상 코드

```swift
// CoreNetwork/Sources/NetworkEndpoint.swift - 사실의 자리
public protocol NetworkEndpoint: Sendable {
    // ...
    /// 이 요청에 Authorization 헤더를 자동 부착할지, 기본 true
    var requiresAuth: Bool { get }
    /// 이 요청을 자동으로 한 번 더 보내도 안전한가(멱등), 재시도 정책의 게이트
    var isIdempotent: Bool { get }
}

extension NetworkEndpoint {
    /// 기본값을 선언이 아니라 HTTP 메서드에서 유도한다 (RFC 7231/9110의 정의 그대로)
    public var isIdempotent: Bool {
        switch method {
        case .get, .put, .delete: true      // 몇 번을 보내도 서버 상태가 같다
        case .post, .patch: false           // 부수효과(토큰 발급, 생성...)가 중복될 수 있다
        }
    }
}
```

```swift
// CoreNetwork/Sources/Pipeline/RequestInterceptor.swift - 행동의 자리
public protocol RequestInterceptor: Sendable {
    /// 전송 직전의 요청을 받아 꾸민 요청을 돌려준다 (예: Authorization 부착)
    func adapt(_ request: URLRequest, endpoint: some NetworkEndpoint) throws -> URLRequest
    /// 요청이 실패했을 때 재시도 여부를 결정한다. 주의: 하나라도 .retry면 다시 보낸다 (OR 결합)
    func retry(_ endpoint: some NetworkEndpoint, dueTo error: Error, attempt: Int) async -> RetryDecision
}
```

```swift
// CoreNetwork/Sources/Pipeline/TransientErrorRetryInterceptor.swift - 게이트의 실제 위치
// 멱등 게이트: 비멱등 요청이면 에러 종류를 보기도 전에 재시도를 포기한다
guard endpoint.isIdempotent else { return .doNotRetry }
```

## 3. 사실과 행동 - 코드 배치의 기준

### 3-1. "토큰을 인터셉터로 분리했다"의 정확한 의미

토큰 처리는 두 조각인데, 인터셉터로 나간 것은 **행동뿐**이다:

| 조각 | 내용 | 위치 |
|---|---|---|
| **사실** | "이 요청은 인증이 필요하다" | `NetworkEndpoint.requiresAuth` - **엔드포인트에 남았다** |
| **행동** | 그 사실을 보고 Authorization 헤더를 붙인다 | `AuthTokenInterceptor.adapt` - 이것만 나갔다 |

멱등성도 이미 정확히 같은 배치다:

| 조각 | 내용 | 위치 |
|---|---|---|
| **사실** | "이 요청은 두 번 보내도 안전하다" | `NetworkEndpoint.isIdempotent` (HTTP 메서드에서 기본값 유도) |
| **행동** | 그 사실을 보고 재시도를 결정한다 | `TransientErrorRetryInterceptor.retry` - **이미 인터셉터** |

즉 "토큰처럼 멱등성도 분리하자"는 이미 완료된 일이고, `isIdempotent`를 인터셉터로 옮기면 오히려 이 대칭이 깨진다.

### 3-2. 왜 사실은 엔드포인트에, 행동은 인터셉터에 두나

- **사실은 자기 자신을 아는 곳에**: "검색 API가 멱등한가"는 그 API의 속성이다. 엔드포인트 선언부(`SearchUserAPI`)는 method/path/headers 같은 사실들을 이미 선언하고 있고 `requiresAuth`/`isIdempotent`도 그 목록의 연장이다.
- **행동은 파이프라인에**: 정책은 교체/조합/테스트의 단위다. 새 정책 = 새 타입 하나 + Composition Root의 배열에 끼우기(NetworkSession은 수정 없이). 정책 단위 단위테스트도 여기서 나온다.
- **사실의 선언 부담도 설계**: `isIdempotent` 기본값을 HTTP 메서드에서 유도하므로([RFC 9110 9.2.2절](https://www.rfc-editor.org/rfc/rfc9110#section-9.2.2)의 멱등 메서드 정의 그대로), OAuth 토큰 교환(POST)은 **아무 선언 없이도** 자동 재시도에서 빠진다.

## 4. 결합 규칙 - 분리해도 되는가를 결정하는 것

### 4-1. 이 파이프라인의 결합 규칙은 OR다

`RequestInterceptor.retry`의 규칙: **"하나라도 `.retry`면 다시 보낸다."** 즉 `.doNotRetry`는 "재시도를 막는다"가 아니라 **"나는 재시도할 이유가 없다"일 뿐**이라서, 다른 인터셉터의 `.retry`를 막지 못한다.

### 4-2. 게이트 분리 시뮬레이션 - 뚫리는 과정 

"멱등 게이트만 `IdempotencyGateInterceptor`로 빼면 어떨까"를 그대로 굴려보면:

```
POST 요청이 badConnection으로 실패했다.

IdempotencyGateInterceptor        -> POST라서 .doNotRetry   (재시도 이유 없음)
TransientErrorRetryInterceptor    -> 일시적 에러라서 .retry  (게이트가 빠진 버전)
-----------------------------------------------------
OR 결합                            -> 재시도 실행 !!  게이트가 뚫렸다
```

POST 재전송 = 부수효과 중복 실행(토큰 이중 발급, 결제 이중 청구류)이다. 게이트는 **재시도를 결정하는 정책 안쪽의 첫 번째 guard**여야만 안전하다 - 실제 코드가 정확히 그렇게 돼 있다(2절 세 번째 코드).

### 4-3. 일반화 - 같은 함정이 나오는 자리들

결정을 합치는 시스템에서 "이 판단을 별도 컴포넌트로 분리해도 되는가"는 결합 규칙이 정한다.

- **any-allow(OR)**: 하나만 허용해도 통과 -> 거부 조건은 분리 불가, 허용하는 쪽 내부의 guard로
- **all-must-allow(AND)**: 전원 허용해야 통과 -> 거부 조건을 독립 컴포넌트로 분리 가능

재시도 정책(이 사례), 권한 체크 체인, 유효성 검사 파이프라인이 전부 같은 구조의 문제다. **분리 리팩터링 전에, 결정이 어떻게 합쳐지는지부터 확인**해야 한다.

## 5. 사실이 행동이 되는 시점 - Idempotency-Key

멱등성 관련 코드가 인터셉터 자격을 얻는 순간은 **행동이 생길 때**다. 대표 사례가 Stripe 등이 지원하는 Idempotency-Key 패턴이다. 클라이언트가 POST에 고유 키 헤더를 실으면 서버가 같은 키의 중복 실행을 막아 주기 때문에, 비멱등 요청도 안전하게 재시도할 수 있다. 이런 API를 쓰게 되면 두 가지가 생긴다.

- `IdempotencyKeyInterceptor` - `adapt`에서 POST 요청에 UUID 키 헤더 **부착** (요청을 바꾸는 행동 -> 인터셉터 자격)
- 해당 엔드포인트만 `isIdempotent = true` 오버라이드 -> 재시도 게이트가 열린다.

예외가 필요한 엔드포인트(Idempotency-Key를 받는 POST 등)가 생기면 그 엔드포인트만 `isIdempotent`를 오버라이드하면 된다. GitHub API는 이 키를 지원하지 않으므로 지금은 만들지 않는다 - "사용처가 생기면 그때" 기준 그대로.

## 6. Alamofire와의 대응

| 이 레포 | Alamofire | 역할 |
|---|---|---|
| `RequestInterceptor.adapt` | `RequestAdapter.adapt` | 전송 직전 요청 변형 |
| `RequestInterceptor.retry` + `RetryDecision` | `RequestRetrier.retry` + `RetryResult` | 실패 후 재시도 결정 (백오프 포함) |
| 두 훅을 한 protocol에 + 기본 구현 | `Interceptor` (Adapter+Retrier 합성) | 필요한 훅만 구현 |

구조가 같으므로 "Alamofire 없이 만들면?"과 "Alamofire의 adapt/retry는 왜 그렇게 생겼나?"에 같은 답을 쓸 수 있다.

## 7. 정리

- **재시도**는 인터셉터 체인의 retry 훅에서 결정하고, **멱등성**은 엔드포인트가 `isIdempotent`로 선언한다. 배치 기준은 사실과 행동의 분리다 - "인증이 필요한가, 두 번 보내도 안전한가"는 엔드포인트의 자기 선언이고, "그 사실을 보고 헤더를 붙인다, 재시도를 결정한다"는 파이프라인의 정책이다.
- 멱등 게이트를 별도 인터셉터로 빼지 않은 이유는 결정이 합쳐지는 방식에 있다. 이 파이프라인은 하나라도 `.retry`면 재시도하는 OR 결합이라 `.doNotRetry`가 재시도를 막지 못하고, 게이트를 분리하면 다른 인터셉터의 `.retry`에 뚫린다. 그래서 재시도를 결정하는 정책 안의 첫 guard로 뒀다.
- 멱등성 기본값은 RFC 9110의 정의대로 HTTP 메서드에서 유도한다. 그래서 OAuth 토큰 교환 같은 POST는 아무 선언 없이도 자동 재시도에서 빠진다.

보충 정리:
- **POST 재시도가 위험한 이유** - 비멱등이라 부수효과(생성/발급/청구)가 중복 실행될 수 있다. 특히 타임아웃은 "서버가 처리 못 함"이 아니라 "응답만 못 받음"일 수 있어서 더 위험하다.
- **rate limit(403/429)은 멱등 GET인데도 재시도하지 않는 이유** - 멱등 게이트와 별개의 조건이다. 기계적 재시도는 제한을 더 길게 만들 뿐이라, 게이트를 통과한 뒤에도 에러 종류로 다시 거른다.
- **그래도 POST를 재시도하고 싶다면** - Idempotency-Key 패턴(5절). 키 부착이라는 행동이 생기니 그때는 인터셉터가 맞다.
- **백오프의 위치** - `RetryDecision.retry(after:)`에 실려 온다. 지연 계산도 정책의 일부라 인터셉터가 계산하고, NetworkSession은 받은 숫자만큼 기다릴 뿐이다 (0.5 -> 1.0 -> 2.0 지수 증가).
